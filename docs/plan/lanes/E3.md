**Epic:** E3, `docs/plan.md`. **Prompt:** `docs/plan/prompts/L1-E3.md`.
**Status lives in `docs/roadmap.md` (M3), not here.**

**L0 `acc:` line, verbatim:**

> `dira check "add a background daemon"` exits non-zero against a fixture ledger
> containing dec-0060 and names both the conflicting entry and its `why_not`;
> `dira check` on a compliant plan exits 0; a superseded decision stops being
> enforced and its superseder is enforced instead.

Four lanes. `E3-L1` fixes the contract and the adversarial fixture corpus; `E3-L2`
builds the verb; `E3-L3` extends it across ledger boundaries under `cst-0003`;
`E3-L4` makes supersession change enforcement.

## Cross-epic prerequisites

Not lane dependencies — epic-level. Stated because a false `none` deadlocks a wave.

| Lane | Needs | Why |
|---|---|---|
| E3-L1 | nothing buildable | fixtures + one decision entry; data and prose only |
| E3-L2 | **E0** (Go module, `go test ./...`, schema-validation test) and **E1** (storage interface + entry reader) | the check is a reader over the same query path as `dira why` |

**Package paths below assume E0 lands `internal/<domain>` with the binary at
`cmd/dira`.** If E0 chooses another layout the paths shift; the predicates do not.

## Three calls this L1 makes, so four lanes do not each make them differently

These are mechanics, not new direction. E3-L1 records them as one decision entry so
they are auditable rather than folklore.

### 1. The enforcement set is explicit and closed

A check that enforces the wrong states is either a wolf-crier or a sieve. Both kill
`int-0001` mechanically.

| Entry | Enforced? | Matched against |
|---|---|---|
| `decision` / `accepted` | yes | each `alternatives[].option` — the roads not taken |
| `decision` / `rejected` | **yes** | the entry's own `title`/subject — the thing we said no to. Rejected decisions are permanent substrate; a check reading only `accepted` misses the point of the epic |
| `decision` / `staged` | **no** | nothing. Staged is a regex-tier guess (`dec-0003`). Enforcing an unconfirmed guess is the fastest route to the check being switched off |
| `decision` / `superseded` | no | nothing, but a match is *reported* and redirected to its superseder (E3-L4) |
| `constraint` / `active` | yes | title + tags + body, including constraints inherited through `derives_from` (E3-L3) |
| `constraint` / `superseded` | no | nothing |
| `intent`, `question`, `note` | no | never enforcement substrate. They appear inside `why_not` prose; they are not matched independently |

### 2. A private entry is cited ref-only **always**, not conditionally

`cst-0003` rule 3 and `docs/design.md` §7 say ref-only "where a check must cite a
private constraint in a public context". Implemented literally that requires the
binary to classify its own stdout as public or private, which it cannot do — a pipe
into a PR body looks like a terminal. So: **any entry with `private: true`, and every
entry read from a `tier = "person"` ledger, is cited by ref (`me:cst-0002`) and never
by text, in every mode, including `--json`.** This is strictly tighter than the
constraint, so it supersedes nothing. A leak here is a security bug (`cst-0003`).

### 3. Exit codes

`0` compliant · `2` at least one cited conflict · `1` reserved for dira's own errors
(unreadable ledger, bad flag). Distinguishing 1 from 2 is what lets the pre-plan seam
tell "you are contradicting yourself" apart from "dira is broken" — and hook callers
must never treat 1 as a verdict.

### E3-L1 — Fix the conflict-detection contract and build the adversarial corpus

Decide *how* a free-text plan is matched against the ledger, record it as an entry with
its rejected alternatives, and build the fixture ledgers plus the labeled corpus every
later lane is graded against. The corpus is the only thing standing between this epic
and a check that cries wolf; it is written **before** the matcher exists and frozen by
checksum, so the matcher cannot be tuned by deleting the rows it fails.

The decision must weigh at least: lexical matching in the binary (idf-weighted
distinctive terms + exact multiword phrases); binary-emits-candidates with the live
session adjudicating; and a new optional schema field carrying explicit trigger terms.
Binding on whichever wins: **`dira check` must reach a non-zero exit with no model, no
network, and no agent present** (`dec-0003`, `cst-0004`). A design where the exit code
depends on an agent having adjudicated is not admissible; an additive
agent-assist mode on top of a deterministic floor is.

**acc:** `go test ./internal/enforcer -run TestCorpusWellFormed` passes over
`internal/enforcer/testdata/corpus.yaml`, which holds ≥40 labeled candidate plan
strings referencing ≥8 distinct entries, of which ≥15 are compliant near-misses that
each share ≥2 content words with an enforced entry and must **not** conflict; every
expected-conflict row names an entry id that exists under
`internal/enforcer/testdata/ledgers/` and quotes a `why_not` substring that literally
appears in that entry file; `internal/enforcer/testdata/corpus.sha256` matches the
corpus; and `grep -rl "conflict detection" .dira/entries/` returns exactly one
`dec-*.md` that validates against `schema/entry.schema.json` and carries ≥3
`alternatives`, each with a non-empty `why_not`, one of them the embed-a-model-client
option citing `dec-0003`.

**risk:** the corpus is authored by someone who has not yet had to satisfy it, so it
can be simultaneously unachievable and unfalsifiable — 15 near-misses chosen to be
lexically indistinguishable from real conflicts would make E3-L2 impossible rather than
merely hard. Near-misses must be plausible things a person would actually type, not
adversarial word salad.

**entries:** implements the `dira check` design in `docs/design.md` §7; constrained by
`dec-0003` (no model client), `cst-0004` (no network/service), `cst-0002` (no sixth
kind — a schema change may add a field, never a kind), `dec-0002` (one file per entry).
The fixture `dec-0060` reproduces the README/marketing example exactly.

### E3-L2 — Implement `dira check` end to end over a single ledger

The verb: read the enforcement set from one local ledger, match, render, exit. Includes
the human-readable format and `--json`, because the renderer and the engine meet at a
verdict struct and splitting them would put a handoff mid-lane.

The human format is **frozen by marketing**, not by taste: `.agents/product-marketing.md`
§6 pre-registers this exact block as E8's primary demo asset, ≤20s and unnarrated.
Reproduce it, golden-file it, and treat a diff as a break.

**acc:** `go test ./internal/enforcer` reports ≥90% of the corpus's expected-conflict
rows detected **with the correct entry id cited** and **zero** compliant rows flagged,
having first asserted the corpus matches `corpus.sha256`;
`dira check "add a background daemon to track run state"` against
`internal/enforcer/testdata/ledgers/daemon` exits 2 and matches
`internal/enforcer/testdata/golden/daemon.txt` byte-for-byte, that golden containing
the `rejected alternative`, `why_not`, and `revisit_if` lines for dec-0060;
`dira check "write the checkpoint file atomically"` against the same ledger exits 0 and
emits no `✗`; a matched alternative with no recorded `revisit_if` renders an explicit
"none recorded — supersede <id> to reopen" line rather than omitting the field; the
fixture's `state: staged` decision is cited by nothing; and `dira check --json`
validates against a committed `schema/check.schema.json`.

**risk:** zero false positives on 15 deliberate near-misses may not be reachable by
lexical matching at ≥90% recall. If it is not, the honest output is a reported
precision/recall curve and a proposal to move the threshold or to change the contract —
**not** a quietly edited corpus, which is why the checksum assertion is inside the
`acc:` line. This is the one lane where a cheap model grinding for green has an obvious
cheat available.

**entries:** `docs/design.md` §7 (message format), `.agents/product-marketing.md` §6
and §10 (the block is a launch asset; voice is unhyped, no exclamation, no "AI-powered"),
`dec-0003`, `cst-0004`, `int-0001`.

### E3-L3 — Inherit constraints across ledger boundaries without leaking private text

Resolve `[parents]` from `.dira/config.toml` (the `{ path, ref }` shape already
committed there), read the parent ledger **read-only**, collect its active constraints,
evaluate them in the child, and cite private ones by ref only. Also: an unreachable
parent must be *reported*, never silently skipped — a check that quietly drops inherited
constraints is a firewall with a hole in it, and it fails silently in exactly the
configuration a public clone has.

**acc:** with a fixture parent ledger (`tier = "person"`) holding an active constraint
whose body contains the sentinel `SENTINEL-PRIVATE-TEXT` and a child ledger whose
`[parents]` points at it, `dira check "start a second side project"` from the child
exits 2, cites `me:cst-0002`, and its combined stdout+stderr contains zero occurrences
of `SENTINEL-PRIVATE-TEXT` and zero occurrences of the parent constraint's title — the
same assertion holding for `--json`; a sha256 over the child's sorted
`.dira/entries/` is identical before and after the run (read-time only, `cst-0003`
rule 2); no dira invocation in the test writes any byte under the parent ledger path
(assert by parent-tree digest, `cst-0003` rule 1); and with `[parents]` pointing at a
nonexistent path the same command still exits on its *local* verdict while printing a
line naming the unresolved parent and the number of constraints not evaluated.

**risk:** this lane lands the `[parents]` reader that E5 also needs, before E5 has
answered `qst-0001`. Kept safe by scope: resolve a parent that is present on this
machine, and report when it is not. It must **not** decide what a public clone displays
for a dangling private ref — E5 owns that surface. A lane that answers it in passing
pre-empts another epic's work.

### E3-L4 — `dira supersede`, proven by a red-to-green enforcement flip

Supersession that changes what is enforced, not just what is labeled. One test moves
from red to green across a single command: the same input conflicts before and is clean
after, and the enforced entry has changed identity.

**acc:** in one test against `internal/enforcer/testdata/ledgers/supersede`,
`dira check "add a background daemon"` exits 2 citing dec-0060; after
`dira supersede dec-0060 --with dec-0061`, the identical command exits 0, no output
cites dec-0060, and a conflict fabricated against dec-0061's own alternatives is now
cited instead; dec-0060's file reads `state: superseded` with `updated` bumped,
dec-0061 carries a `supersedes` edge to dec-0060, both still validate against
`schema/entry.schema.json`, and no other entry file changed (tree digest);
`dira check` on an input matching the now-superseded dec-0060 emits an informational
line naming dec-0061 and **no** `✗`; and `dira supersede me:cst-0002 --with cst-0005`
exits non-zero, writes nothing, and leaves the parent ledger byte-identical.

**risk:** supersede is the only write verb in this epic, so it is where a partial
mutation can corrupt the ledger — two files change and `dec-0002`'s one-write-per-
mutation property does not cover a two-entry edit. Decide and test the failure mode
(write the superseder's edge first, or refuse and roll back) rather than discovering it
after a crash mid-command.

**entries:** `dec-0002` (one file per entry; the two-file edit is the exception that
needs a stated failure mode), `cst-0003` rule 1 (no upward write), `dec-0001`
("overruling this is a one-line supersede" — dira's own ledger is the acceptance test
for this verb), `dec-0009` (if `mirror.adr` is on, the mirrored ADR is regenerated,
never read back).

## Problems this plan does not solve, stated rather than hidden

1. **Nobody owns invoking `dira check`.** L0 scopes E3 to the verb; E2 scopes the skill
   and the hooks. "Runs before predicates are drafted" is therefore unowned, and a
   perfect enforcer that nothing calls enforces nothing. Needs an L0 decision: add the
   pre-plan seam to E2's scope, or add a fifth E3 lane.
2. **"Surface `revisit_if` in every conflict message" is not satisfiable for constraint
   conflicts.** `revisit_if` exists only on `alternative` in
   `schema/entry.schema.json`; a `constraint` has no such field, and the README's own
   example block shows `cst-0004` cited without one. Either constraints get "supersede
   this constraint to change it" as their escape hatch, or the schema gains an
   entry-level `revisit_if` — folded into E3-L1's decision, and flagged here because the
   epic prompt reads as though the schema already supports it.
3. **No `acc:` line here is already green.** There is no Go code in the repo at all —
   `find . -name '*.go'` is empty. All four lanes start red, which is the intended
   state; there is nothing to report as a pre-passing defect.

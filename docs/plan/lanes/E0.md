# E0 — Foundations: a Go project that ships (L1 lanes)

**Epic:** E0 · **L0:** `docs/plan.md` §E0 · **Prompt:** `docs/plan/prompts/L1-E0.md`
**Lane count:** 5 (bound is 6) · **Owner of status:** `docs/roadmap.md`, not this file.

**L0 `acc:` (verbatim):** `go build ./...` succeeds; `go test ./...` passes with a
schema-validation test that fails when a fixture entry violates `entry.schema.json`;
a tagged push produces a downloadable darwin-arm64 + linux-amd64 binary;
`brew install kazi-org/tap/dira` installs it.

### E0-L1 — Stand up the Go module and the `dira` command skeleton

**acc:** `go build ./...` and `go vet ./...` succeed on the version pinned in
`go.mod`; `gofmt -l .` prints nothing; `go list -deps ./cmd/dira` contains **no
non-stdlib module** (the cobra-exclusion check — test-only deps are invisible to this
command by construction); `dira --help` exits 0 and names every registered
subcommand; an unknown subcommand exits **2** with usage on **stderr** and nothing on
stdout; `dira --version` prints `dev` from a plain `go build` and prints exactly
`1.2.3` when built with `-ldflags "-X main.version=1.2.3"`.

**risk:** the layout gets designed for the whole product instead of for E0 and
arrives with a cobra-shaped router, a config loader, and empty packages for E1–E6 —
at which point `int-0002`'s cold-start promise is already spent and `dec-0001` bought
nothing. The `go list -deps` clause is the forcing function.

**Note for later epics:** the zero-third-party-dep clause is an E0 predicate, not a
constitutional one. E1 legitimately adds a YAML parser and a SQLite driver to the
command path. Superseding it there is expected; silently deleting it is not.

**entries:** `dec-0001` (Go, and what it forfeits), `int-0002` (one binary, no
runtime, cold start is the UX), `cst-0004` (works with the network unplugged).

### E0-L2 — Make the ledger self-validating in Go

The highest-value lane in the epic. Nothing in the repo validates the ledger today —
`docs/roadmap.md`'s claim that the entries "all validate against the schema, no
dangling edges" rests on an uncommitted throwaway script, so it is an assertion, not
a gate.

**acc:** `go test ./...` validates all real `.dira/entries/*.md` green **and** fails
on every file in `internal/ledger/testdata/invalid/`, where that directory contains
at minimum: an id violating the id pattern, an unknown top-level field, a decision
with no `alternatives`, an `intent` in state `accepted`, an id whose prefix
disagrees with its `kind`, a filename that disagrees with its `id`, a
`derives_from` edge pointing at an entry that does not exist, and a file with no
frontmatter. The test names the offending file and the violated rule in its failure
message, and a negative fixture that unexpectedly **passes** fails the suite.

**risk:** the lane delegates the whole job to a JSON Schema library and stops there.
Four of the eight required negative fixtures are invisible to `entry.schema.json` as
written — `edge.to` has no pattern (`$defs/ref` is defined and never referenced), id
and `kind` are independent, and filenames are outside the schema's world. A
validator that only shells out to a schema library passes the vacuous half of the
predicate and leaves the ledger able to rot exactly where it actually rots.

**entries:** `dec-0002` (one file per entry — the invariant being defended),
`cst-0002` (the five kinds are closed; the `kind` enum is the mechanism),
`dec-0004` (no execution status is ever a stored state).

### E0-L3 — Gate every push on build, vet, format, and test

**acc:** a push to a branch of `kazi-org/dira` produces a **green** Actions run
whose log shows `go test ./...` executing a non-zero count of tests; a second push
carrying one deliberately unformatted file **and** one failing test produces a
**red** run naming both; every `uses:` in the workflow is pinned to a 40-character
commit SHA; the Go toolchain is taken from `go.mod` rather than restated in the
workflow.

**risk:** a workflow that is green because it ran nothing. The executed-test-count
clause and the deliberate red push exist because "CI is green" is the single easiest
false victory in this epic. Second risk: `permissions:` left at the default write
scope on a public repo.

**entries:** none bind this lane directly; it is the mechanism by which `E0-L2`'s
gate is actually a gate.

### E0-L4 — Turn a tag into downloadable binaries

**acc:** `goreleaser check` passes and `goreleaser build --snapshot --clean`
produces both `darwin/arm64` and `linux/amd64` artifacts locally; pushing tag
`v0.0.1-rc.1` to `kazi-org/dira` creates a GitHub Release carrying a
darwin-arm64 archive, a linux-amd64 archive, and a checksums file, each downloadable
by an anonymous `curl`; the darwin-arm64 binary extracted from that archive runs and
prints exactly `0.0.1-rc.1` for `dira --version`; and `CGO_ENABLED=0` is set for
every build target.

**risk:** the tag→binary path is built to depend on release-please activation
(`vars.RELEASE_AUTOMATION`, org PR-creation settings, a PAT) and therefore cannot be
verified until a human provisions secrets. Keep the `on: push: tags: v*` path
working standalone — `GITHUB_TOKEN` can create a Release in its own repo, so this
lane's `acc:` is verifiable today with zero secrets. Layer release-please on top as
`workflow_call`, exactly as `kazi/.github/workflows/release-please.yml` does.

**Cross-epic consequence, stated deliberately:** `CGO_ENABLED=0` is what makes
darwin binaries cross-buildable on Linux runners and keeps the one-static-binary
promise of `int-0002`. It also forecloses `mattn/go-sqlite3` for E1's derived cache
and pushes E1 toward a pure-Go SQLite (`modernc.org/sqlite`). E0 will make that
choice de facto; it deserves a `.dira/` decision entry rather than being discovered
in E1.

**entries:** `dec-0001` (goreleaser is the named forfeit being paid here),
`int-0002` (one static binary, no runtime to install), `cst-0004` (no account
needed to obtain or run it).

### E0-L5 — Ship `dira` through the existing Homebrew tap

**acc:** `Formula/dira.rb` lands in the **existing** `kazi-org/homebrew-tap` with
`Formula/kazi.rb` byte-unchanged in the same commit range; `brew install
kazi-org/tap/dira` on darwin-arm64 installs a binary whose `dira --version` equals
the released tag minus its leading `v`; `brew test kazi-org/tap/dira` passes; and a
**second** release bumps the formula's version and sha256 with no human edit to the
tap.

**Human-gated prerequisite:** the auto-bump needs a `HOMEBREW_TAP_TOKEN` secret on
`kazi-org/dira` — a fine-grained PAT with `contents:write` on
`kazi-org/homebrew-tap` only. Only the repo owner can mint it. Plan and land
everything else without it: mirror kazi's convention where the publish step
**warns and skips** when the token is absent rather than failing the release, so the
binary pipeline stays green while the brew half waits on a human.

**risk:** two release pipelines now write to one tap repo. A force-push, a
`git add -A`, or a formula generator that rewrites the directory clobbers
`Formula/kazi.rb` and breaks `brew install kazi` for every kazi user — a failure in
another product, caused by this lane. The byte-unchanged clause is that guard.
Secondary risk: `qst-0004` (name collisions) is still open; the fully-qualified
`kazi-org/tap/dira` install path is unaffected by a `dira` in homebrew-core, so this
lane does not block on that question.

**entries:** `dec-0001` ("a second formula in the existing tap" — this is that),
`int-0002` (`brew install dira && dira init` is the whole onboarding),
`qst-0004` (open, non-blocking for the tap path).

## Deliberately not a separate lane

**Docs.** `README.md` already documents install and usage for a binary that does not
exist. Rather than a thin docs lane that goes stale the moment another lane lands,
each lane owns the prose that its own `acc:` makes true: `E0-L1` owns
build-from-source, `E0-L4` owns the release/download path, `E0-L5` owns the
`brew install` instructions. Each L2 prompt states this.

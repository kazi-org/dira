# E7 — Apps — lanes (L1)

**Status of this file:** lane level only. **No L2 prompts exist for this epic and none
should be written yet.** `dec-0007` sequences the paid apps deliberately — the team tier
ships "when teams pull for it, **not before**", and the apps are bought by people who
already use dira, so they cannot create the audience that produces those people
(`dec-0010`'s "build the paid apps first" alternative, rejected). Planning tasks now
optimizes the wrong end of the funnel.

**Gated on:** E6 shipping (the apps reuse the storage interface and the design system)
**and** adoption evidence per `dec-0007`. E7-L1 exists to make that second gate
structural rather than a note in a plan file.

**Epic-level predicate.** `docs/plan.md` §E7 has **no `acc:` line** — every other
non-blocked epic has one. `L1-E7.md` instructs "see the E7 section of `docs/plan.md`,
verbatim", so this is a plan defect, not a reading failure. The nearest authoritative
statement is roadmap M7's exit criterion, which I have adopted as the epic predicate;
the lead should either ratify it into `docs/plan.md` or replace it:

> A decision confirmed on a phone appears in the next session's brief on the laptop,
> with no dira server involved.

## E7-L1 — Encode the E7 start gate as an enforceable ledger entry

**Beyond the provisional scope in `L1-E7.md`,** which lists only the backend, the PWA,
and the bundle. Included deliberately: this epic's defining property is that it is
gated, and a gate recorded only in a plan file is exactly the artifact nobody re-reads
(`int-0001`). Encoding it makes `dira check` refuse the work until the trigger fires.
Strike this lane if the lead disagrees — it changes nothing else in the epic.

**acc:** a decision entry in `.dira/entries/` records a numeric threshold for starting
E7 (a specific install count and a specific count of public rendered ledgers, each with
the command that measures it named in the entry); `dira check "build the paid iOS and
desktop apps"` exits non-zero against the live ledger, naming that entry and
`dec-0007`'s "when teams pull for it, not before"; and against a fixture ledger where
the threshold entry is superseded as met, the same `dira check` exits 0.

**risk:** any threshold chosen today is a guess. The predicate deliberately tests the
*mechanism*, not the number, and the entry must carry a `revisit_if`.

**entries:** implements `dec-0007`; relies on `dira check` and supersession from E3
(`dec-0009`'s enforcement path if that is where it lands); constrained by `cst-0002`
(this must be a `decision`, not a new entry kind).

## E7-L2 — Implement the `github` storage backend behind the existing interface

**acc:** the storage-interface conformance suite that drives `local` passes unchanged
against `github` over recorded HTTP fixtures (one table-driven test, both backends); and
a request-count assertion proves each entry mutation issues **exactly one** Contents API
`PUT`, preceded by at most one `GET` for the blob sha — the test fails if the write path
issues any further request. No code above the interface distinguishes the two backends:
a build-tag or grep test asserts `net/http` and the GitHub client are imported only
inside the backend package.

**risk:** discovering mid-lane that some mutation (a supersession touching two entries,
an edge added to a second file) is not one file write. If so, `dec-0002`'s "one write per
mutation" is violated by the *ledger design*, not by this backend, and that finding
belongs upstream in E1 rather than being papered over with a two-`PUT` special case.

**entries:** implements `dec-0005` (local | github, same operation shape) and `dec-0002`
(one file per entry ⇒ one `PUT`); constrained by `cst-0004` — the backend talks to
GitHub, the user's own infrastructure, and no dira-operated endpoint exists anywhere in
it. `dec-0005`'s rejected "run a dira sync server" alternative is the line not to cross.

## E7-L3 — OAuth device flow, token custody, and conflict surfacing

**acc:** `dira` obtains a GitHub token by OAuth device flow and stores it in the OS
keychain — a test that dumps the repo tree and the process environment and greps for the
token value fails on any hit; a simulated `409`/stale-sha response surfaces as a named
conflict identifying both entry versions and exits non-zero (never an overwrite); a
mutation interrupted mid-write and then retried leaves **exactly one** entry file, not
two; and with credentials absent every read-only command still works against the `local`
backend with the network refused.

**risk:** silent-overwrite is the failure that would make dira untrustworthy for the one
thing it stores. The conflict test must assert the *pre-existing* content survives, not
merely that an error was printed.

**entries:** `dec-0005` (OAuth over the Contents API), `cst-0004` (no account required
for core capability — this lane adds an optional credential, never a mandatory one),
`dec-0007` (privacy-as-product: the token and the data stay with the user).

---

## E7-L4 — Ship the PWA from the same SPA source as `dira ui`

**acc:** the PWA and `dira ui`'s embedded bundle are produced from one source tree — a
test asserts the shared bundle's content hash is byte-identical across both build
targets, so a fork is a failing build; the installed PWA renders a ledger read-only from
its cache with the network refused; and its screens pass the same gates E6 passes — the
contrast matrix reports 0 failures and the render comparison against
`docs/design/screens/` is within the pixel tolerance recorded in `DESIGN.md`.

**risk:** a PWA needs a served origin, which invites a dira-hosted one. It must be
either the user's own GitHub Pages or the read-only renderer of `dec-0010` — additive
and storing nothing. Anything else is a `cst-0004` violation.

**entries:** `dec-0010` (the renderer is read-only, stores nothing, and the CLI behaves
identically whether it exists or not), `dec-0005` (a third consumer of the same storage
interface), `cst-0004`, and E6's design system.

---

## E7-L5 — Package and price the iOS + desktop bundle

**acc:** a tagged push produces, from CI, a notarization-validated macOS archive and an
App Store-validated iOS archive; a build-time test fails if the shipped `Info.plist` or
entitlements name any network host other than the GitHub API and the user's own
configured git remote; and the StoreKit product is a non-consumable scoped to a major
version — a fixture receipt for major N grants no entitlement for N+1.

**risk:** store review and notarization are schedule risk outside the repo's control,
and `dec-0007` records that one-off revenue is a decaying curve per release with brutal
App Store discovery absent the OSS funnel. Neither is fixable by planning; both argue
for this lane being last.

**entries:** `dec-0007` (one-off purchase, pay-once-per-major-version, and its recorded
caveats), `cst-0004` (the host allowlist test is that constraint made mechanical),
`.agents/product-marketing.md` §8 — never charge for the CLI, hooks, the skill,
`dira ui`, or the public renderer.

# E4 — Derived status · lanes (L1)

**Epic:** E4 — Derived status (`docs/plan.md` §E4, roadmap M4)
**L0 `acc:` (verbatim):**

> against a recorded `portfolio --json` fixture, `dira map` reports every bucket
> correctly and distinguishes execution-blocked from decision-blocked; with the `kazi`
> binary absent `dira map` still renders ledger-side buckets and states that execution
> status is unavailable rather than guessing; no status value is ever persisted into an
> entry file.

**Five lanes.** L1 and L2 are independent and parallel — L1 touches kazi and never the
ledger, L2 touches the ledger and never kazi. L3 joins them, L4 renders, L5 proves the
two invariants the epic exists for. Status lives in `docs/roadmap.md`, not here.

`E0` / `E1` are **epic-level** dependencies. Concretely E4 needs a buildable Go module
with a command skeleton (E0) and the entry reader plus the derived-cache query layer
including an **inbound-edge index** (E1). No lane below may stub those.

## What I verified myself, and where the prompt and `dec-0008` are wrong

Read this section before planning any task in this epic. Every claim below was checked
against `/Users/dndungu/Code/kazi-org/kazi` source **and** a live
`kazi portfolio --json` on this machine (kazi at `/usr/local/bin/kazi`) on 2026-07-29.
The prompt's `cli.ex:1254` / `cli.ex:4249` / `portfolio.ex:55` citations are all
accurate, and `portfolio` is indeed absent from `Kazi.CLI.Schema` (registered commands
are exactly `apply`, `plan`, `status`, `bus` — `schema.ex:427`). The following is what
those citations do not say.

**1. There are two bucket vocabularies, not one.** `@bucket_order`
(`portfolio.ex:55`) — `done | running | blocked | todo | planned` — governs
`totals.rows[].bucket` and the top-level `todo` / `blocked` arrays. But
`by_repo[repo]`'s keys and `fleet_remote[].bucket` use a **different, three-value**
enum, `@type bucket :: :in_progress | :stuck | :complete` (`portfolio.ex:38`). The
JSON emits **no top-level `running` and no top-level `done` array** — verified, the
top-level keys are exactly `blocked, by_repo, fleet_remote, kind, planned, rate,
schema_version, todo, totals`. So `dec-0008`'s and `docs/design.md` §6.2's "Bucket
enum: `done | running | blocked | todo | planned` — a clean map onto §6.1" is true for
the *aggregate counts only*. Per-goal `running` / `done` is not on that surface.

**2. `by_repo` cannot answer "what is this goal's status".** `local_by_repo/2`
(`portfolio.ex:~416`) groups **every** run, while `five_buckets/2` first dedups via
`latest_run_per_ref/1`. Measured on this machine: **63 `by_repo` entries covering 35
distinct `goal_ref`s, with 20 refs carrying more than one run** — `warnings-clean`
appears 4 times across 4 worktrees. `run_entry/1` emits `{goal_ref, run_id, status}`
and **no timestamp**, so nothing in the JSON says which of those 4 is current.

**3. `by_repo.in_progress` is not "live".** `bucket/2` is `converged → :complete`,
`stuck | over_budget | error → :stuck`, **everything else → `:in_progress`**. Real
output contains `{"status":"terminated", ...}` filed under `in_progress`. Mapping
`in_progress → In progress` reports dead runs as live.

**4. Consequence — the join key is `goal_ref`, and per-goal truth comes from
`kazi status <ref> --json`.** That command *is* registered in `Kazi.CLI.Schema`
(`schema.ex:345`), resolves a run **or** a proposal, and returns `status`,
`converged`, `iteration`, `predicates`, `release_ref`, `observed_at` — latest-iteration
semantics, one authoritative answer per ref. Measured cost ≈0.65s per invocation. So
E4's read surface is a **hybrid, and the hybrid is not a compromise**: one
`portfolio --json` call for the roll-up, the `prop→goal` bridge and blocked
attribution (which `status` does not carry — its documented `status` values are only
`converged` / `in_progress`), plus one `status <ref> --json` per ref dira actually has
a `realized_by` edge for. Never key anything on repo: `repo_label/1` falls back to the
last two path segments when the workspace is gone, and on this machine **every**
`by_repo` key is a worktree path like `kazi-worktrees/p-warnings-clean-9479baf7-…`.

**5. The `prop → goal_id` bridge is durable, and lives only in `planned`.** Proposal
rows are `{proposal_ref, goal_id, idea, status}`. Top-level `planned` is
`planned_entries()`, which unions `"proposed"` **and** `"approved"` and is **not**
filtered by whether a run exists; `ProposedGoal`'s status enum is
`proposed | approved | rejected` with no "applied"
(`read_model/proposed_goal.ex:45`), so an approved proposal stays in `planned`
permanently. Two consequences: a **rejected** proposal vanishes from portfolio
entirely, so `realized_by: kazi:prop-…` pointing at one is *unresolvable* and must be
said so rather than silently demoted to "to be planned"; and `planned` overlaps both
`todo` (approved-minus-running) and live runs, so **summing `planned + todo + blocked`
double-counts**. Use `totals.rows` for counts; never re-derive them.

**6. `rate.empty?` keeps the Elixir question mark. `totals.empty` does not.**
Verified: `"rate":{"total":60,"green":22,"empty?":false,"delta":16}` beside
`"totals":{"empty":false,"base":42,…}` — `portfolio_totals_json/1` renames the key,
`fleet_rate/1`'s map is passed through verbatim. The Go tag is `json:"empty?"`.

**7. `portfolio` is machine-global, not workspace-scoped.** Byte-equivalent output
from `/tmp` and from a repo. `dira map` in repo X receives the whole fleet's portfolio
and must filter to the `goal_ref`s its own `realized_by` edges name.

**8. `schema_version` is 2 and is shared across kazi's entire `--json` surface**
(`@run_schema_version 2`, `cli.ex:95`), so it will bump for reasons unrelated to
portfolio. A hard equality gate would false-alarm on an unrelated kazi release. Treat
an unknown version as **contract drift** — parse best-effort, say the version moved,
fail the contract test in CI — not as an error that blanks the map.

**9. `blocked` carries `cause ∈ {dag, over_budget, error, stuck}`** plus `blocker`,
and `cause: dag` entries come from `DagSnapshot` over the `:starmap_roadmap_goal`
app-env goal. On a machine without that configured the DAG path emits nothing — all 12
blocked rows here are `stuck`/`over_budget`. A recorded fixture must be **hand-extended**
to cover `dag` and non-empty `fleet_remote`; neither occurs naturally in the recording.

**10. Exit codes:** `kazi portfolio --json` → 0; a bad argument or unknown command → 2
(and prints help to stdout). So exit code alone is insufficient — validate that stdout
parses and that `kind == "portfolio"`.

**11. The entry schema already forbids the naive version of "status stored".**
`schema/entry.schema.json` is `additionalProperties: false` with a closed `properties`
list, and its `state` enum contains no execution value. E0 wires that validator as a
test. So "grep entry files for status fields" is **near-vacuous** on its own — the
prompt's suggested test would be green before E4 starts. E4-L5's `acc:` is therefore
written against what the schema *cannot* catch. This is the one already-green predicate
in this epic, and it is called out rather than shipped.

**Documentation correction owed:** `dec-0008` §1 and `docs/design.md` §6.2 both assert
the five-bucket enum maps cleanly onto the §6.1 join table. Points 1–4 above show it
does not. E4-L1's first task records this as a `.dira/` entry and corrects §6.2; it does
not silently diverge from an accepted decision.

### E4-L1 — Build the kazi read surface — a typed client over `portfolio --json` and `status <ref> --json`, pinned to recorded fixtures

**acc:** `go test ./internal/kazi` passes against `testdata/kazi/` holding ≥4 recorded
fixtures (a populated multi-goal `portfolio --json`, an empty one, one hand-extended to
carry all four `cause` values `dag|over_budget|error|stuck`, and one with non-empty
`fleet_remote`), asserting: `rate.empty?` and `totals.empty` both decode to a non-zero
field (the JSON keys genuinely differ); `by_repo` values decode under
`in_progress|stuck|complete` while `totals.rows[].bucket` decodes under
`done|running|blocked|todo|planned`, and a fixture that swaps the two enums **fails**
to decode rather than decoding as a zero value; `Snapshot()` with no `kazi` on `PATH`,
with a stub exiting 2, with a stub printing non-JSON, with a stub printing JSON whose
`kind != "portfolio"`, and with a stub that sleeps past the deadline each returns
`Unavailable` carrying a distinct machine-readable reason and a nil snapshot — and in
no case a value a caller could mistake for an empty portfolio; a `schema_version` other
than the pinned `2` yields a snapshot flagged `ContractDrift` naming the observed
version, not an error; and `Status(ref)` decodes both `kind: "run"` and
`kind: "proposal"` fixtures and reports a ref kazi does not know as `NotFound` distinct
from `Unavailable`.

**risk:** pinning the wrong thing. `portfolio` is unregistered and unpinned upstream
(nothing in kazi's suite asserts its shape as a public contract), so the recorded
fixture *is* the contract — and a fixture recorded from one machine's state encodes
that machine's accidents: zero `fleet_remote`, zero `cause: dag`, worktree-shaped
`by_repo` keys. A client tested only against the natural recording will be confidently
wrong on the paths that never occurred locally. The secondary risk is treating the two
enums as one, which decodes silently to zero values instead of failing.

**entries:** implements `dec-0008` (integrate only through `--json` and hooks) and
`dec-0004` (derive, never store); constrained by `cst-0004` (no network — the client
shells out to a local binary and nothing else), `int-0002` (no daemon; do **not** reach
for `kazi bus`, per `qst-0005`), `dec-0003` (no model client). Corrects `dec-0008` §1
per point 1 above.

### E4-L2 — Derive the ledger-side buckets and decision-blocked detection, with no kazi involved

**acc:** `go test ./internal/status -run 'TestLedger|TestDecisionBlocked'` passes over
`testdata/ledgers/` where: an accepted decision with no `realized_by` edge lands in
`ToBePlanned` and an active intent with none does too; an **open** question carrying
`blocks → dec-X` puts `dec-X` in `DecisionBlocked` naming the question's id and title,
found **without `dec-X` itself carrying any edge** (edges live on the subject, so this
requires the inbound-edge index, not a scan of `dec-X`); flipping that question to
`state: answered` moves `dec-X` back to `ToBePlanned` with no other diff; a question
blocking an entry whose own state is `superseded` produces no `DecisionBlocked` row;
`achieved` and `abandoned` intents are reported as their own terminal ledger-side
groups and never as `ToBePlanned`; and `go list -deps ./internal/status` shows
`os/exec` is **not** reachable from this package, with the tests additionally passing
under an emptied `PATH`.

**risk:** decision-blocked degenerates into a footnote. It is the one row no execution
tracker can produce (`dec-0004`, `docs/design.md` §6.1), and it is also the cheapest to
get subtly wrong: the edge lives on the *question*, so a naive implementation that
reads only the entry under inspection finds nothing and reports `ToBePlanned` — an
answer that looks plausible and is the precise failure the bucket exists to prevent.
The `acc:` line's "without `dec-X` carrying any edge" clause is the guard.

**entries:** implements `dec-0004` (rows 1 and 6 of the join table) and
`schema/entry.schema.json`'s `blocks` semantics; constrained by `cst-0002` (five kinds,
closed — no new kind for "blocked"), `dec-0002` (one file per entry, so the reverse
index is derived and disposable).

### E4-L3 — Join the two into dec-0004's six buckets — ambiguity and unresolvable refs reported, never guessed

**acc:** `go test ./internal/status -run TestJoin` passes over E4-L1's pinned fixtures
paired with E4-L2's fixture ledger: `realized_by: kazi:prop-<ref>` resolves through the
portfolio `planned` array to its `goal_id` and then to that goal's bucket;
`realized_by: kazi:goal-<id>` resolves directly; a `prop` ref absent from `planned`
(rejected upstream) yields an `UnresolvedRef` row naming the ref and is **never**
reported as `ToBePlanned`; a `goal_ref` carrying conflicting `by_repo` runs — the
fixture must include the recorded `warnings-clean` case with 4 runs — resolves via
`Status(ref)` and records `Source: "kazi status"` on the row, while the same case with
`Status` unavailable yields `Ambiguous` naming the conflicting statuses rather than
picking one; a run with `status: "terminated"` is never reported as `InProgress`; a
`Completed` row carries kazi's evidence **by reference only** (`run_id` plus
`release_ref`, with a test asserting no predicate vector is copied into the row); and
the roll-up counts a caller can read equal `totals.rows` from the fixture, with a test
that fails if `planned`, `todo` and `blocked` are ever summed.

**risk:** silent single-answer resolution. With 20 of 35 refs multi-run on a real
machine, "take the first `by_repo` entry" passes any test whose fixture happens to be
single-run and is wrong most of the time in production — and wrong in the direction that
matters, since a converged run and a stuck retry of the same goal sit side by side. The
second risk is cost: `Status` per ref at ≈0.65s makes `dira map` linear in
`realized_by` edges, so this lane must bound the calls to refs the map actually needs
and say what it does at 100 edges.

**entries:** implements `dec-0004`'s join table in full and `dec-0008` seam 1;
constrained by `dec-0004`'s "never asserts doneness — it inherits it" (hence evidence by
reference), and `cst-0004`.

### E4-L4 — Build `dira map` — the intent tree grouped by why, with roll-ups and `--json`

**acc:** `go test ./internal/cli -run TestMap` passes against golden files: `dira map`
over the fixture ledger emits the intent tree grouped by `derives_from` parent in the
shape `docs/design.md` §6.4 records, each intent's roll-up line's counts equalling the
sum of its own children's buckets (a test that mutates one child's bucket and asserts
the roll-up changes); all six `dec-0004` buckets appear across the golden files, each
with a distinct label; an entry with no `derives_from` parent appears under an explicit
unparented group, proved by a test asserting rendered-entry count equals ledger-entry
count so nothing is dropped; `--json` emits a documented shape whose bucket names are
dira's six, not kazi's five or three; and `dira map --json` is byte-identical across two
consecutive runs on an unchanged ledger after deleting the single top-level
`observed_at` field.

**risk:** rebuilding `kazi portfolio` in dira's clothing. The lane's whole reason to
exist is that `kazi portfolio` groups by **goal** and `dira map` groups by **why**
(prompt, `docs/design.md` §6.4); a renderer that prints buckets with an intent header
bolted on top has reproduced the thing it was supposed to replace. The roll-up-per-why
and the unparented group are the structural differences, and the second risk is dropping
entries — an entry that is in no bucket and under no parent silently vanishing is worse
than a wrong label, because nothing on screen indicates a gap.

**entries:** implements `dec-0004` and `docs/design.md` §6.4; constrained by
`cst-0001`'s spirit (this is a human surface, not the brief — do not let it grow into a
second context injection), `.agents/product-marketing.md` for every line of copy, and
`docs/design/screens/s2-index.html` for vocabulary.

### E4-L5 — Prove the two invariants end to end: honest degradation, and status never stored

**acc:** `go test ./test/acceptance -run 'TestDegradation|TestNeverStored'` passes: with
no `kazi` on `PATH`, `dira map` exits 0, renders the ledger-side buckets, prints an
explicit unavailability line naming the reason, **and** its stdout contains none of the
execution-bucket labels — asserted as the *absence* of the "converged", "in progress"
and "execution-blocked" strings, not merely the presence of a banner; the same holds for
a stub kazi exiting 2, one printing garbage, one printing a foreign `kind`, and one
hanging past the deadline, each naming a distinct reason; and never-stored is proved by
three checks the entry schema cannot make — the sha256 of every file under `.dira/` is
unchanged across a `dira map` run and that run still exits 0 with `.dira/` mounted
read-only; a lint over an execution-status vocabulary list finds no match in any entry's
`tags` or edge `note`, with a deliberately poisoned fixture proving the lint actually
fails; and `go list -deps` shows the map command's package graph does not import the
ledger **writer** package at all.

**risk:** self-passing gates. Every clause here is one the implementing lane could
weaken into a tautology — a banner test that passes because the banner is the only
output, a grep test that passes because the schema already forbids the field
(point 11), a read-only test that passes because nothing was read either. Each clause is
therefore two-sided: an absence assertion paired with a poisoned fixture that must fail.
This lane should be owned by someone other than E4-L4's owner.

**entries:** proves `dec-0004` (both invariants: derived-at-read-time, and degrade
without guessing) and `cst-0004` (works with nothing installed but dira); constrained by
`schema/entry.schema.json` and `int-0003` (the moment status is stored, dira is the
tracker it exists to delete).

## Boundaries worth stating, so two lanes do not build the same thing

- **The drift row is E5's, not E4's.** `docs/design/screens/s2-index.html` shows it, but
  `docs/plan.md` §E5 and roadmap M5 own the orphan-work drift flag, and E5 is **blocked
  on `qst-0001`**. E4-L4 emits the *unparented group* so E5 can flag it; E4 must not
  implement tier-crossing ref resolution.
- **The web presentation is E6's.** E4 owns `dira map` (terminal) and its `--json`
  shape; `s2-index.html` is E6's implementation target. E4 must expose **all six**
  buckets even though the design screen shows four labels (`converged`, `in motion`,
  `to be planned`, `blocks this`) — collapsing six into four is a presentation decision
  E6 makes from a complete input, not a derivation E4 pre-truncates.
- **Filing the upstream ask is E9's.** E4 must be fully correct with `qst-0005` issue 1
  never landing; that is what pinning a fixture buys. No E4 lane waits on E9.
- **Creating `realized_by` edges is E2's** (and its automatic path is blocked on
  `qst-0005` issue 2). E4 only *consumes* them.
- **`dira why` and the chain renderer are E1's.** E4-L4 groups by parent; it must not
  grow a second chain walker.
- **The inbound-edge index is E1's.** E4-L2 consumes it. If E1 has not shipped one,
  E4-L2's first act is to say so, not to build a private one.

*how* the write happens, not of the formula's content. kazi's own `tap-bump` job

stages `Formula/kazi.rb` **by name**, never `git add -A`, never force-pushes, and
that exact shape is what has kept the tap safe so far. Reusing goreleaser's `brews:`
pipe would hand the same directory a second, differently-audited write path this
session has not read the source of. Porting kazi's shape — a small generator plus a
named-path commit — costs one more package than the native pipe and keeps the one
property that matters auditable in this repo's own code.

## What is already known, so no task re-derives it

**A formula, not a cask** (`docs/plan/lanes/E0.md`'s constraint) — Homebrew casks
are macOS-only and this lane's `acc:` requires the same tap serve a linux-amd64
binary too, matching `Formula/kazi.rb`'s existing `on_macos`/`on_linux` shape.

**`qst-0004` is answered and does not block this lane.** The name "dira" is clear on
every channel dira actually ships through (`.dira/entries/qst-0004.md`); a `dira` in
homebrew-core would not affect the fully-qualified `kazi-org/tap/dira` install path.
What it does forbid: this lane's tasks must not plan a bare `brew install dira` as
the documented onboarding command, only the fully-qualified form. `int-0002`'s own
achieved-when line uses the short form — that discrepancy is `qst-0004`'s to close,
not this lane's, and T6 states the fully-qualified form deliberately rather than
"fixing" `int-0002`'s prose.

**New Go packages in this lane must stay off `dec-0005`'s allowlist, the same
constraint `docs/plan/tasks/E0-L4.md` names.** `internal/ledger/boundary_test.go`
scans every package in the module for `os`/`os/exec`/`path/filepath` in **non-test**
files. T2's publish-orchestration logic — cloning a repo, staging one path, pushing
— genuinely needs those imports to do its job, so it cannot live as a non-test `.go`
file inside `internal/`. It lives in `scripts/tap-bump.sh` instead (a shell script,
invisible to `go list`, matching how `scripts/ci-local.sh` already works in this
repo), and the Go test that proves its behavior is a `_test.go`-only package
(`internal/tapbump`, no sibling implementation file), exactly the shape
`docs/plan/tasks/E0-L4.md` uses for `internal/relbuild` and `internal/relwf`. T1's
generator, by contrast, is pure — no filesystem, no exec — and lives as ordinary Go
in `internal/tapformula` with no exemption needed at all.

**The risk this lane exists to guard against, restated as the one thing every task
below must be able to demonstrate failing.** kazi's own `tap-bump` job does
`git add Formula/kazi.rb` — a single named path, never `-A`, never `--force` — for
exactly one reason: a generator or a force-push touching the whole `Formula/`
directory clobbers `Formula/kazi.rb` and breaks `brew install kazi` for every kazi
user, a production failure in another product caused by this one. T2's `acc:`
therefore proves the byte-unchanged property **both ways** — the real script leaves
`kazi.rb` untouched, and a deliberately broken variant (one that does `git add -A`)
is shown breaking it — because a guard that has never been observed to catch
anything is a hope, not a guard (`docs/lore.md` L-0001).

### E0-L5-T1 — Formula generator: pure function, byte-golden tested

Takes a version string and, per target (darwin-arm64, linux-amd64), a download URL
and a sha256, and returns the formula's bytes. Touches no filesystem and shells out
to nothing, so it needs no exemption from `dec-0005`'s check at all.

**Files:** `internal/tapformula/generate.go`, `internal/tapformula/generate_test.go`,
`internal/tapformula/testdata/golden.rb`

**acc:** `go test ./internal/tapformula -run TestGenerateFormula` passes:

- given a fixed version and both targets' `{url, sha256}`, the generated bytes are
  byte-identical to `testdata/golden.rb`;
- the golden fixture contains `class Dira < Formula`, one `on_macos` block and one
  `on_linux` block each carrying its own `url` and `sha256`, a `version` line equal
  to the input, a `# Generated by ... Do not hand-edit.` header (mirroring
  `Formula/kazi.rb`'s own header, per the lane's constraint that the formula is
  generated and never hand-edited), and a `test do` block whose body asserts the
  installed binary's `--version` output equals the formula's declared `version` —
  the lane's own correction to kazi's weaker `--help`-contains-`kazi` assertion,
  because a version check is what actually catches a formula pointing at a stale
  release;
- each of the four required per-target fields (url, sha256, per target) returns a
  named error and no output bytes when empty, checked individually against an
  otherwise-fully-valid input so each negative case is proven against a positive
  baseline in the same run, not in isolation.

**Both sides:** the golden-match assertion is proven able to fail by mutating one
input field (e.g. the linux sha256) and observing the diff land on the expected
line, not merely "some difference exists."

**depends_on:** none · **verifies:** `dec-0001`, `int-0002`

### E0-L5-T2 — Publish script proven against a local fixture tap, never a real one

**Files:** `scripts/tap-bump.sh`, `internal/tapbump/publish_test.go` (test-only
package, no sibling implementation file)

`scripts/tap-bump.sh` takes a tag, a checksums file (or the two url+sha256 pairs
directly), a target git remote, and an optional token. It invokes T1's generator
(via `go run ./internal/tapformula/...` or an equivalent thin entry point T1 also
provides — the generator package decides its own invocation surface; this task only
requires that the script call it rather than re-implement formula rendering in
shell), clones the target remote into a temp directory, writes
`Formula/dira.rb`, stages **only that path**, commits, and pushes — or, if no token
is supplied, prints a warning naming `HOMEBREW_TAP_TOKEN` and exits 0 without
touching the clone at all.

**acc:** `go test ./internal/tapbump -run TestPublish` passes, against a local bare
git repository (the test's own fixture, standing in for `kazi-org/homebrew-tap`)
seeded with an arbitrary `Formula/kazi.rb`:

- run with a token and fixture inputs: the resulting default-branch commit touches
  exactly one path, `Formula/dira.rb`; that file's bytes equal T1's generator output
  for the same inputs; `Formula/kazi.rb`'s bytes are sha256-identical to the seeded
  fixture before and after;
- run with the token variable unset: the bare repo's ref is unchanged afterward (no
  clone, no commit, no push attempted), the script exits 0, and its output names
  `HOMEBREW_TAP_TOKEN`;
- run a second time with the same inputs after the first succeeded: no new commit is
  produced (idempotent — a second identical publish is a no-op, mirroring
  `internal/skill.Install`'s `UNCHANGED` precedent that `docs/plan/tasks/E2-L3.md`
  already established for this repo);
- `scripts/tap-bump.sh` itself is grepped for `-A` immediately after `git add` and
  for `--force`/`-f` on any `git push` — both absent — as a static backstop
  alongside the behavioral proof, since a script that happens to behave correctly
  today with one flag left in dead code is a landmine for the next edit.

**Both sides:** a deliberately broken copy of the script that does `git add -A`
instead of `git add Formula/dira.rb` is run against the same fixture, and
`Formula/kazi.rb`'s bytes are observed to change (because the fixture is seeded with
a stray unrelated file the broken variant also picks up) — proving the
byte-unchanged assertion is capable of catching the exact failure this task exists
to prevent, not merely capable of passing.

**depends_on:** `E0-L5-T1` · **verifies:** `dec-0001`

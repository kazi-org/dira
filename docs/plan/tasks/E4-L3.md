## What is already known, so no task re-derives it

**Every measured fact this lane leans on is in `docs/plan/lanes/E4.md`'s "What I verified
myself" section, points 1–7, cited by number in the tasks below rather than re-quoted in
full each time.** The two that decide this lane's shape: point 2 — `by_repo` is **not**
deduped and carries **no timestamp**, 63 entries over 35 `goal_ref`s on a real machine, 20
multi-run, `warnings-clean` at 4 — and point 3 — `by_repo.in_progress` catches a
`status: "terminated"` run, so the bucket cannot be trusted as "live" on its own.

**The specific thing not to do, repeated from the L2 prompt because it is this lane's
single largest risk:** resolve a multi-run goal by taking the first `by_repo` entry. It
passes any fixture that happens to be single-run and is wrong on the real machine's
majority case, in the direction that matters — a converged run and a stuck retry of the
same goal sit side by side with nothing in `by_repo` to order them. T3's `acc:` line
names the control that catches this.

**The join surface this lane adds to `internal/status`, fixed here so nothing downstream
needs a conversation:**

```go
package status

// StatusFunc is kazi.Status's shape, injected rather than called directly so
// this lane's own tests never shell a binary and so a caller (E4-L4) can wrap
// it with a call counter to enforce a fan-out bound.
type StatusFunc func(ctx context.Context, ref string) (*kazi.RunStatus, *kazi.ProposalStatus, error)

// MaxStatusCalls bounds Join's fan-out. At kazi's measured ≈0.65s per Status
// call (docs/plan/lanes/E4.md point 4), an unbounded join over N realized_by
// edges is O(N) wall-clock against a human waiting on a terminal command.
// T3's acc: line states what Join does at the bound, not just what the bound
// is.
const MaxStatusCalls = 25

// Join resolves every entry in candidates (accepted decisions and active
// intents carrying a realized_by edge — the caller, E4-L4, selects them via
// index.Selector{WithEdge: ledger.EdgeRealizedBy}) against snap. snapErr, when
// non-nil, is exactly the error kazi.Snapshot() returned (an *kazi.Unavailable
// or nil *kazi.Snapshot with a wrapped drift note) — Join never receives a
// snapshot it should not trust, because E4-L1 already enforces that at the
// source.
func Join(ctx context.Context, candidates []*ledger.Entry, snap *kazi.Snapshot, snapErr error, statusFn StatusFunc) ([]Row, error)

// Totals reads dec-0004's roll-up counts directly from snap.TotalsRows and
// never re-derives them by summing Planned/Todo/Blocked buckets (dec-0008
// point 5 — that sum double-counts, because planned overlaps both todo and
// live runs).
func Totals(snap *kazi.Snapshot) []kazi.TotalsRow
```

`join.go` and `join_test.go` land in `internal/status`, the same package E4-L2 built —
this lane must not edit `types.go`, `ledger.go`, `blocked.go` or `terminal.go`. `Row`,
`Bucket`, `Source`, `KaziEvidence`, `AmbiguousDetail` and `UnresolvedDetail` are already
declared there (see `docs/plan/tasks/E4-L2.md`'s "What is already known"); this lane is
the first to actually populate `Evidence`, `Ambiguous` and `Unresolved`, and the first to
set `Source` to anything other than `SourceLedger`.

### E4-L3-T1 — Ref parsing and resolution: `prop-` through `planned`, `goal-` direct, unresolvable named

`realized_by` targets are `kazi:prop-<ref>` or `kazi:goal-<id>` (`schema/entry.schema.json`
`$defs/edge`'s own two examples — both legal, both must resolve). A `prop-` ref resolves
through `snap.Planned`, matching `ProposalRef`, to its `GoalID`; that id is then the join
key for everything downstream. A `prop-` ref **absent** from `snap.Planned` — a proposal
rejected upstream, which portfolio drops entirely (lane doc point 5) — is not
`ToBePlanned` and not silently skipped; it is a `Row{Bucket: <caller decides, see below>,
Unresolved: &UnresolvedDetail{Ref: target, Reason: "..."}}`. This task also settles which
`Bucket` an unresolved row carries: since none of the six named buckets fit "the ref names
nothing kazi knows about," the row's `Bucket` is left as the zero value (`""`) and `E4-L4`
is told (in this task's own note, not re-litigated by E4-L4) to render unresolved rows
under their own heading rather than folding them into any of the six.

**Files:** `internal/status/join.go` (new, `parseRealizedBy` and the resolution half),
`internal/status/join_test.go`

**acc:** `go test ./internal/status -run TestJoinResolve` passes over E4-L1's `testdata/kazi/`
fixtures paired with a small ledger fixture this task adds (`testdata/ledgers/realized-by/`,
one entry per ref form): a `kazi:prop-<ref>` entry whose `<ref>` appears in
`portfolio-populated.json`'s `Planned` resolves to that proposal's `GoalID`, asserted by
value; a `kazi:goal-<id>` entry resolves to `<id>` directly with no lookup into `Planned`;
a `kazi:prop-<ref>` entry whose `<ref>` does **not** appear in `Planned` produces a `Row`
with `Bucket == ""` and `Unresolved.Ref == target`, and is asserted **absent** from
whatever `ToBePlanned`-shaped output the caller might otherwise conflate it with — a test
that fails if the unresolved row's `Bucket` is ever `ToBePlanned`; and a `realized_by`
target matching neither form (missing the `kazi:` prefix, or a third verb) produces a
named parse error rather than a silently-empty result.

**Both sides:** the rejected-proposal case is proven able to fail against a resolver that
falls back to `ToBePlanned` on a lookup miss (the plausible-looking wrong answer the lane
doc's point 5 warns about) and proven to pass on the real resolver's `Unresolved` report.

**depends_on:** `E4-L1`, `E4-L2` (types) · **verifies:** `dec-0004`, `dec-0008`

### E4-L3-T2 — Bucket mapping: kazi's surfaces onto dec-0004's six, `terminated` excluded

Once a `realized_by` target resolves to a goal id, map what kazi says about that goal onto
dec-0004's six-bucket vocabulary. This is where the two-enum split (`dec-0008` point 1)
and the `terminated`-under-`in_progress` trap (point 3) are handled explicitly rather than
inherited by accident from a single shared type — `internal/kazi`'s `RepoBucket` and
`RowBucket` are already distinct Go types (E4-L1-T3), so this task's job is the mapping
function, not re-fighting the decode.

Concretely: `blocked[].cause` (any of the four) maps to `ExecutionBlocked`; a `by_repo`
entry whose `Bucket == kazi.RepoComplete` maps toward `Completed`, but **only** after T3's
multi-run resolution confirms it (this task defines the mapping *rule*; T3 wires the
fan-out that makes it safe to apply to a specific run rather than an unordered set); and a
`by_repo` entry whose raw `Status == "terminated"` is excluded from mapping to `InProgress`
regardless of its `Bucket` value, because `bucket()` folds it into `RepoInProgress`
upstream and this is precisely the case the acc: line names by name.

**Files:** `internal/status/join.go` (the mapping function, same file as T1, later wave)

**acc:** `go test ./internal/status -run TestJoinBucketMapping` passes: a
`portfolio-all-causes.json`-derived goal with `cause: "dag"` (and each of the other three)
maps to `Bucket: ExecutionBlocked`, asserted for all four causes in one table-driven test
so no cause is silently missed; a single-run `by_repo` entry with `Status: "terminated"`
maps to anything **other than** `InProgress` — this task does not have to decide its final
resting bucket (T3/T6 may resolve it to `Ambiguous` or something else entirely), only that
it is never `InProgress`, asserted as a negative; and a single-run entry with
`Bucket: RepoComplete` and a normal `Status` string maps toward `Completed`.

**Both sides:** the `terminated` exclusion is proven able to fail against a mapping that
trusts `RepoBucket` alone (ignoring the raw `Status` field E4-L1-T3 exposes specifically
for this check) and is shown reporting `InProgress` for the terminated fixture before the
real mapping is shown not to.

**depends_on:** `E4-L3-T1` · **verifies:** `dec-0004`, `dec-0008`

### E4-L3-T3 — Multi-run resolution: bounded `Status` fan-out, `Source` recorded, `Ambiguous` when unresolved

The lane's hardest task, and the one the "specific thing not to do" section above exists
for. A `goal_ref` whose `by_repo` runs disagree (the `warnings-clean`-shaped case, 4 runs
on the real machine) is resolved by calling `statusFn(ctx, ref)` — never by picking a
`by_repo` entry — and the resulting row records `Source: SourceKaziStatus`. When
`statusFn` itself returns an `*kazi.Unavailable` (kazi could answer the portfolio call but
not this specific status call — a real, distinct failure mode from the whole-snapshot
degradation T6 covers), the row is `Ambiguous`, naming every **distinct** raw `Status`
string seen across the conflicting runs, not a summary. A goal with only one `by_repo` run
needs no `Status` call at all and is resolved with `Source: SourcePortfolio` — calling
`Status` for the single-run case would be correct but wasteful, and this task's `acc:`
line asserts the fan-out is skipped there, so the bound below is spent only where it is
needed.

**Files:** `internal/status/join.go` (same file, later wave), `internal/status/join_test.go`

**acc:** `go test ./internal/status -run TestJoinMultiRun` passes:

- against `portfolio-populated.json`'s recorded `warnings-clean` multi-run case (E4-L1-T2's
  corpus, which the fixture README names explicitly) paired with a `statusFn` fake
  returning a definite `converged` result, the resulting `Row.Source == SourceKaziStatus`
  and `Row.Bucket == Completed`;
- the same fixture with `statusFn` returning an `*kazi.Unavailable` error produces
  `Row.Bucket == Ambiguous` (or the zero value with `Row.Ambiguous` set — whichever the
  implementation chooses, consistently with T1's unresolved-row convention) with
  `Ambiguous.Statuses` containing every distinct raw `Status` string observed across
  `warnings-clean`'s runs, asserted as a set (order-independent) with length ≥ 2 — a test
  that fails if the fixture's own multi-run case collapses to one status, since that would
  make this the wrong fixture to prove the clause;
- a single-run goal is resolved with **zero** calls to `statusFn` — asserted by a counting
  wrapper around the fake, not by inference — and `Row.Source == SourcePortfolio`;
- fan-out is capped at `MaxStatusCalls`: a synthetic ledger fixture with more than
  `MaxStatusCalls` multi-run `realized_by` edges results in exactly `MaxStatusCalls` calls
  to `statusFn`, and every candidate beyond the bound is reported the same way an
  `Unavailable`-degraded ambiguity is reported (naming the bound as the reason, not
  silently omitted from the result) — the acc: line's "say what it does at 100 edges"
  clause, made concrete.

**Both sides:** the "take the first `by_repo` entry" shortcut is written inline in the test
as a deliberately wrong resolver (mirroring E4-L2-T4's naive-resolver control) and run
against the `warnings-clean` fixture, asserted to produce a **different** bucket than the
real resolver on at least one of the fixture's runs — proving the shortcut is not merely
stylistically worse but observably wrong on the recorded case. The bound clause is proven
able to fail against an unbounded resolver (temporarily disabling the cap in a local test
copy) making more than `MaxStatusCalls` calls, and proven to pass on the bounded one.

**depends_on:** `E4-L3-T2` · **verifies:** `dec-0004`, `dec-0008`

### E4-L3-T4 — `Completed` evidence by reference only

`dec-0004` — dira never asserts doneness, it inherits it. A `Completed` row's evidence is
`run_id` and `release_ref`, nothing else; no predicate vector, no iteration history.

**Files:** `internal/status/join.go` (same file), `internal/status/join_test.go`

**acc:** `go test ./internal/status -run TestJoinEvidence` passes: a `Completed` row's
`Evidence` field is exactly `&KaziEvidence{RunID: ..., ReleaseRef: ...}` populated from the
resolved `kazi.RunStatus`; and — the explicit negative test the lane `acc:` line demands —
`Row` (and `KaziEvidence`) contain **no field** capable of holding a predicate vector,
asserted structurally via `reflect` over `KaziEvidence`'s field set rather than by
inspecting one instance's contents, so the check catches a future field addition rather
than only today's shape.

**Both sides:** the structural assertion is proven able to fail by adding a throwaway
`Predicates []string` field to a **local copy** of `KaziEvidence` defined inline in the
test (not committed to `join.go`) and observing the reflect-based check name it, then
proven to pass against the real, unmodified type.

### E4-L3-T5 — Roll-ups read from `totals.rows`, never summed

`dec-0008` point 5: `planned` overlaps both `todo` and live runs, so summing
`planned + todo + blocked` double-counts. `Totals(snap)` is a passthrough of
`snap.TotalsRows`, and nothing in this lane computes a second set of counts by summing
bucket-specific slices.

**Files:** `internal/status/join.go` (the `Totals` function)

**acc:** `go test ./internal/status -run TestJoinTotals` passes: `Totals(snap)` for
`portfolio-populated.json` is element-for-element equal to the fixture's own
`totals.rows` array, asserted by comparing the decoded slice directly (not by re-summing
and checking the sum matches, which would not catch a totals-recomputation bug); and a
test that constructs a snapshot where `len(Planned) + len(Todo) + len(Blocked) !=
sum(TotalsRows[].Count)` (achievable by hand-editing a copy of a fixture, since `planned`
genuinely overlaps `todo` on the real machine per point 5) asserts `Totals` still returns
`TotalsRows` verbatim and is unaffected by the mismatch — proving the function does not
fall back to summing when the numbers look reconcilable.

**Both sides:** the "never summed" clause is proven able to fail against a version of
`Totals` that returns `len(Planned)+len(Todo)+len(Blocked)` per bucket instead of the raw
`TotalsRows` (written inline in the test as the wrong implementation) and shown to diverge
from the fixture's actual `totals.rows` on the double-counting fixture, then proven to pass
on the real, passthrough implementation.

**depends_on:** `E4-L1` · **verifies:** `dec-0004`, `dec-0008`

### E4-L3-T6 — The degraded join: snapshot `Unavailable` demotes nothing

When `snapErr` is non-nil (kazi absent or erroring at the whole-snapshot level — this is
`kazi.Snapshot()`'s error, distinct from T3's per-ref `statusFn` failures), every
kazi-side bucket becomes an explicit unknown and **no** `realized_by`-carrying entry is
ever reported as `ToBePlanned` — E4-L2-T3 already excludes such entries from its own
output for exactly this reason; this task's job is proving `Join` itself does not
backfill them into something equally wrong.

**Files:** `internal/status/join.go` (same file), `internal/status/join_test.go`

**acc:** `go test ./internal/status -run TestJoinDegraded` passes: calling `Join` with
`snap == nil` and `snapErr` set to each of E4-L1's five `Unavailable` reasons in turn
produces, for every `realized_by`-carrying candidate entry, a `Row` whose `Bucket` is the
unresolved zero value (matching T1's convention) and whose `Unresolved.Reason` names the
specific `snapErr.Reason` string, not a generic "kazi unavailable" — asserted per reason,
not once; `statusFn` is never called in this path, asserted via a counting fake that fails
the test if invoked; and the same candidates, run through `Join` a second time in the same
test with a working `snap` and `nil` `snapErr`, resolve to real buckets — the positive half
that proves the degraded path is not simply "always report unresolved."

**Both sides:** the "never `ToBePlanned`" clause is proven able to fail against a version
of `Join` that returns an empty slice on `snapErr != nil` (looking safe, actually silently
dropping every candidate rather than reporting them unresolved) and is shown to lose
entries the real implementation keeps, distinguishing "reported as unknown" from "silently
absent" — E4-L4's count-conservation test (`docs/plan/tasks/E4-L4.md`) depends on this
task not dropping rows.

**depends_on:** `E4-L3-T2` · **verifies:** `dec-0004`

is the lane's genuine complexity — a fan-out with a bound, two failure modes

built. T6 is one more branch of the same function. T7 is assembly, not new logic.

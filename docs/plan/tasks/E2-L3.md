Two more are load-bearing here and are named where they bite: `dec-0023` (which hook
carries what, and what the `PreCompact` entry therefore is) and `dec-0005` (the import
boundary that decides where the filesystem may be touched).

**Format note.** The `- [ ]` list under *Tasks* is the claimable surface — one line per
task with its id, `verifies:` and `deps:`, which is what `/apply --pool` reads. The `###`

## What is already known, so no task re-derives it

**`hooks/settings.example.json` is the specification, and it is current.** It installs
three entries: `SessionStart` → `dira brief --context --chain 2>/dev/null || true`
(timeout 5), `Stop` → `dira sniff --stage --quiet 2>/dev/null || true` (timeout 10),
`PreCompact` → `dira sniff --deep --stage --all 2>/dev/null || true` (timeout 60). **The
prompt's copy of this table is stale in two places** — it says `dira brief --context` and
`dira sniff --deep --stage`. Take the file, not the prompt. The `--all` in particular was
added after the installed command was measured losing a third of its captures (3 staged
entries with it against 2 without, on the test transcript), so dropping it back to match
the prompt would be a silent regression in exactly the capture this hook exists for.

**Every command string in that file is accepted by the built binary today**, verified
2026-08-10 against a `go build` of `./cmd/dira` in this worktree:

- `dira sniff --deep --stage --all` — `--deep`, `--stage` and `--all` are all registered
  (`cmd/dira/sniff.go:269-272`). `sniff` was missing from the command registry for weeks;
  that is fixed and `dira sniff -h` documents this exact invocation as "the PreCompact
  invocation".
- `dira brief --context --chain` — exits 0 and prints `chain: no parent ledger is
  configured ([parents] in .dira/config.toml is empty)`. **E1-L5 kept the promise
  `docs/plan/lanes/E1.md` made on `--chain`**, which is the specific instance clause (f)
  was written to catch. T7 is what keeps it caught; it does not get to assume it.

So clause (f) is green-able today. It is still worth building, because its job is the
*next* instance of the class, not this one.

**What the `PreCompact` entry is, settled by `dec-0023` and not reopened here.**
`PreCompact` stdout does not reach the model. On exit 0 it is appended to the compaction
summariser's prompt as custom instructions, and that summariser runs with `maxTurns: 1`
and is told in its own prompt that tool calls will be rejected. So the only reader of a
handoff block delivered there structurally cannot call `dira log`. `SessionStart` (whose
matcher values include `compact`) and `Stop`/`SubagentStop` are the seams that do carry
context to the model. **What this lane installs on `PreCompact` is tier-1 capture that
also prints a block** — nothing in this lane's output, usage text or ledger entries may
describe it as a working tier-2 handoff. That claim was already in this repository once,
was false, and was corrected in the same change as `dec-0023`.

**`dec-0005`'s import boundary decides where the filesystem may be touched, and it is
mechanically enforced.** `internal/ledger/boundary_test.go` allows `os` in `cmd/dira` and
explicitly **not** `path/filepath`; `internal/ledger/local`, `internal/index` and two test
harnesses have the other exemptions. `internal/installhooks` is on nobody's allowlist and
must not be added to one. The check reads `go list`'s `.Imports`, which is **non-test
files only** — so `*_test.go` inside `internal/installhooks` may import `os` and
`os/exec` freely, and T1, T3, T4, T5, T7 and T8 all depend on that. What may not import
them is the shipped code.

**E2-L2-T8 already solved the same problem and is the precedent to copy, not re-derive.**
`internal/skill/install.go` decides what to do from bytes alone and names no path: it
takes a two-method `Root` port (`ReadFile`, `WriteFile`), and `cmd/dira/install_skill.go`
backs it with `*os.Root` so `..` and an escaping symlink are refused by the operating
system rather than by string handling. Its `Outcome` vocabulary — `INSTALLED` /
`UNCHANGED` / `REFUSED` — and its reasoning for keeping `UNCHANGED` distinct from
`REFUSED` ("an installer that refused every second run would look identical to one that
protects edits") transfer directly. This lane needs one more method than the skill
installer did, `Remove`, because uninstall can delete a file the install created.

**kazi's implementation is a span splicer, and a `json.Unmarshal` → `json.Marshal` port
cannot satisfy clauses (a) or (c).** kazi validates the bytes with Jason, scans *the same
bytes* into a span tree, and splices insertions in or drops byte spans out
(`/Users/dndungu/Code/kazi-org/kazi/lib/kazi/teach/install_hooks.ex`: `parse_root/2:246`,
`apply_inserts/2:425`, `drop_spans/2:487`). Go sorts map keys and discards formatting, so
a decode/re-encode port would rewrite every line of a file it was asked to merge into —
including the `//`-prefixed documentation keys **this project's own example file uses**.
Port the span approach.

**kazi identifies its own entries by command prefix, never by position**
(`@command_prefix "kazi bus hook "`, `kazi_entry?/2:365`), with the stated reason that a
later task can grow the command's arguments without orphaning installed entries. That is
not hypothetical here: `--all` was added to the `PreCompact` command after the fact. An
installer matching on the whole string would see an older installed
`dira sniff --deep --stage`, not recognise it, and add a second entry beside it — the
session then runs `sniff` twice per compaction, and an uninstall orphans the old one.
T4 owns this and T4's `acc:` names the case.

**The verification standard this lane is held to** (`docs/lore.md` L-0001): a gate is
evidence only once **both** sides have been observed — red on a constructed defect of the
class it claims to catch, **and** green on the untouched correct baseline. Rule 2 is the
one nobody applies. This lane is unusually exposed to rule 1 as well, because its two
headline proofs are both "run a thing and observe that nothing bad happened": T8's
fail-open test passes trivially against a fake `dira` that never fails, and T7's
flag check passes trivially against an extractor that finds no flags. Both carry an
explicit control that the failure path fired.

**`cmd/dira` is one Go package and this lane adds files to it.** These identifiers already
exist there and must be **reused, not redeclared**: `openClaudeRoot` and `claudeRoot`
(`cmd/dira/install_skill.go:152,193`), `claudeDirName` (`:61`), and `probeFlag`,
`commandNames`, `notAFlag`, `unknownFlagReport` (`cmd/dira/skill_covers_test.go:35-41,275,360`).
Two lanes last wave both declared the same type in one package without sharing a file; the
recovery cost more than the check would have. T6 and T7 each name what they reuse.

**One cross-lane merge hazard, stated because it is not this lane's to fix.**
`dira install-skill` is fully built (`cmd/dira/install_skill.go`, `internal/skill/install.go`)
but is **not** in `newApp(...).commands` — E2-L2-T8 is unchecked, and its registry line is
still pending. T6 adds a second line to that same slice. If both land in the same wave the
conflict is one line in `cmd/dira/main.go` and both entries must survive; whoever merges
second keeps both. The help test iterates the registry rather than listing verbs, so no
help assertion changes either way.

### E2-L3-T2 — Make the shipped example the registrations, by embedding it

The prompt asks for a pinned table in Go that a test compares against
`hooks/settings.example.json`. **Do it one step better and remove the drift instead of
testing for it:** put a `hooks/hooks.go` beside the file that `//go:embed`s it, exactly as
`skills/skills.go` embeds `skills/dira/SKILL.md`, and derive the registrations by parsing
those embedded bytes. `skills/skills.go`'s own comment states the reasoning — "a file
embedded where it already lives cannot drift from itself, and needs no drift test to say
so" — and go:embed cannot reach above its own directory, which is why the `.go` file has
to sit in `hooks/`. Nothing is read from disk at run time, so `dira install-hooks` works
from a released artifact with no checkout near it and with the network unplugged
(`cst-0004`), and it starts nothing (`int-0002`).

Each registration carries an **owner prefix** alongside its command and timeout — the
leading substring by which dira recognises its own entry in somebody else's settings file,
mirroring kazi's `@command_prefix`. `SessionStart` → `dira brief`, `Stop` →
`dira sniff --stage`, `PreCompact` → `dira sniff --deep`. Position is never used.

**The `PreCompact` entry is tier-1 capture that also prints a block** (`dec-0023`). Any
comment or usage text this task writes says that and not more.

**Files:** `hooks/hooks.go`, `internal/installhooks/registrations.go`,
`internal/installhooks/registrations_test.go`

**acc:** `go test ./internal/installhooks -run TestRegistrations` passes:

- parsing the embedded bytes yields **exactly three** registrations, in the file's own
  order: `SessionStart` / `dira brief --context --chain 2>/dev/null || true` / 5,
  `Stop` / `dira sniff --stage --quiet 2>/dev/null || true` / 10, `PreCompact` /
  `dira sniff --deep --stage --all 2>/dev/null || true` / 60 — the three events, the three
  command strings and the three timeouts each asserted literally, because this is the one
  place in the lane where a literal is the point;
- every command's first word is `dira`, every command contains both `2>/dev/null` and
  `|| true`, every timeout is > 0 and ≤ 60, and every command **starts with its own
  declared owner prefix** — so a later flag reordering in the example file that would
  break prefix recognition fails here rather than in somebody's settings file;
- the `PreCompact` command contains `--all`, asserted by name with the reason recorded in
  the test's failure message: without it the same transcript stages 2 entries instead of 3;
- the parser is proven able to refuse rather than guess: fed a mutated copy of the example
  with a missing `timeout`, a missing `command`, two commands under one entry, or a fourth
  event, it returns a **named error** and no registrations. A parser that silently yields
  a zero timeout would install a hook Claude Code bounds by its own default, quietly;
- the test runs with its working directory set to a temp directory and still passes,
  demonstrating the bytes are compiled in rather than read from the checkout;
- no non-test file in `internal/installhooks` or `hooks/` imports `os`, `io/fs`, `path` or
  `path/filepath` — asserted here as well as by `go test ./internal/ledger` (`dec-0005`),
  because failing in the package that broke it is worth the four lines.

**Both sides:** each literal assertion is proven able to fail against a mutated copy of the
example (a changed command, a changed timeout, a removed `|| true`) and proven to pass on
the untouched file. The test fails if the parse yields **zero** registrations, which
otherwise satisfies every "every command …" clause vacuously.

### E2-L3-T3 — Build the byte-span JSON scanner and splicer

Validate the bytes with `encoding/json` first — that is the authoritative malformed-JSON
check — then scan **the same bytes** into a span tree recording the byte offsets of every
object member and array element, so an edit is an insertion at an offset or a deletion of
a span. Everything not spliced survives byte-identically because it is never rewritten.
This mirrors `install_hooks.ex:243-259` and is the only reason byte-identical preservation
can be promised at all.

The package still names no path: this file takes `[]byte` and returns `[]byte`.

**Files:** `internal/installhooks/spans.go`, `internal/installhooks/spans_test.go`

**acc:** `go test ./internal/installhooks -run TestSpans` passes, iterating T1's table:

- for every fixture the table marks valid, scanning and re-emitting with an **empty** edit
  set returns bytes with a sha256 equal to the input — including the `//`-comment-key
  fixture, `hooks/settings.example.json` itself, and the unusual-whitespace fixture;
- every fixture the table marks malformed — bad bytes, a non-object root, a non-object
  `"hooks"` value — returns a named error and **no** span tree;
- a single insertion at a computed offset changes exactly the intended byte range,
  asserted by comparing the prefix and suffix around the offset rather than by eyeballing
  the output;
- a span deletion followed by re-insertion of the same text at the same offset is the
  identity (sha256 equal to the original);
- multiple insertions apply back-to-front so earlier offsets stay valid, asserted by a
  fixture needing all three events inserted at once.

**Both sides, and the red control is the design decision itself:** the test contains a
deliberately wrong emitter — `json.Unmarshal` followed by `json.Marshal` — and asserts it
**fails** the round-trip on the `//`-comment-key fixture and on the unusual-whitespace
fixture. That is the class of defect the span approach exists to defeat, so the suite
should be able to show it happening; a round-trip test that passes for both
implementations is not evidence for either. The identity assertion also fails if the valid
fixture set has fewer than five members, since "every fixture round-trips" is trivially
true of an empty set.

**depends_on:** E2-L3-T1 · **verifies:** `dec-0008`

### E2-L3-T4 — Implement install: merge-never-clobber, idempotent, ownership by prefix

Insert the three registrations, creating only what is missing: the file if absent, the
`hooks` object if absent, an event array if absent, an entry if that event holds no dira
entry already. If all three are present the install is a **byte-level** no-op — nothing
written, `UNCHANGED` reported.

The package cannot write anything, so `Install` takes the current bytes and whether the
file exists, and returns what should be written plus an `Outcome` — the same split
`internal/skill.Install` makes, for the same reason. T6 is what performs the write.

**Ownership is decided by the owner prefix from T2, per event array**, following kazi's
`kazi_entry?/2`: an event whose array already holds an entry whose command starts with
that event's prefix contributes no edit.

**Files:** `internal/installhooks/install.go`, `internal/installhooks/install_test.go`

**acc:** `go test ./internal/installhooks -run TestInstall` passes over T1's full table:

- into an **absent** file it produces a minimal settings document containing exactly the
  three registrations and nothing else, which parses as JSON and round-trips through T3;
- into a file holding an operator's own `Stop` hook, that entry is present and
  **byte-identical** afterwards and dira's is added alongside it — asserted by locating
  the operator's entry's bytes before and after, not by counting entries;
- into a file with unknown top-level keys, every such key's bytes survive sha256-identically
  as a span;
- a second install over the first's output produces **no edits at all** and reports
  `UNCHANGED`; the caller writes nothing, so the file's sha256 is unchanged;
- **the orphan case, named because it has already happened once:** a settings file holding
  `dira sniff --deep --stage` (the pre-`--all` command) under `PreCompact` is recognised
  as dira's, and install adds **nothing** beside it. Matching on the whole command string
  instead would install a second entry and run `sniff` twice per compaction;
- **the other side of that recognition:** a settings file holding an operator's own
  `dira why dec-0003` hook under `Stop` is **not** recognised as dira's, and dira's `Stop`
  entry is added alongside it. A prefix broad enough to swallow any `dira …` command would
  silently leave the session with no capture at all;
- a partially-installed file (one event present, two missing) gains exactly the two
  missing entries and the present one is untouched;
- the malformed fixtures produce a named error, no output bytes, and no `Outcome`;
- no case ever removes or reorders a pre-existing array element, asserted by comparing
  every pre-existing element's bytes before and after across the whole table.

**Both sides:** the merge-preservation assertions are proven able to fail against a build
whose emitter re-encodes rather than splices (T3 already carries that wrong emitter, so
this test reuses it rather than writing a second one) and proven to pass on the real
implementation. The idempotence assertion fails if the first install produced no edits
either — "no edits on the second run" is worthless if the first run also did nothing.

**depends_on:** E2-L3-T2, E2-L3-T3 · **verifies:** `dec-0008`

### E2-L3-T5 — Implement uninstall: the exact inverse, including the deletion decision

Remove exactly the spans install added; everything else is untouched. If the file's bytes
equal what a fresh install creates, the file *is* what install created and nothing has
written to it since, so removing the file restores the pre-install state — absence —
exactly (`install_hooks.ex:152-160`). An uninstall with nothing installed is `UNCHANGED`,
not an error.

Only entries **wholly** owned by dira are removed — kazi's `wholly_kazi_entry?/2`: an
entry mixing an operator's command with dira's is never removed. An event array left with
no other entries loses its key; a `hooks` object left with no other keys is removed
entirely; each removal span is the exact inverse of the corresponding install insertion.

The package deletes nothing. The deletion decision is returned as data (a flag on the
result) and T6 acts on it — the same boundary the write crosses.

**Files:** `internal/installhooks/uninstall.go`, `internal/installhooks/uninstall_test.go`

**acc:** `go test ./internal/installhooks -run TestUninstall` passes over T1's full table:

- for every valid fixture, install-then-uninstall yields bytes whose sha256 equals the
  pre-install bytes exactly;
- for the absent-file case, install-then-uninstall returns the delete-the-file decision,
  and for **every** other case it does not — a `{}` an operator wrote is never deleted;
- an operator's own hook entry under the same event survives an uninstall byte-identically,
  and an entry mixing an operator's command with dira's is **not** removed;
- uninstall with no dira entries present produces no edits and reports `UNCHANGED`;
- uninstall on an absent file reports `UNCHANGED` and is not an error;
- uninstall on the malformed fixtures returns a named error and no output bytes;
- **an entry a human has since edited** — dira's command with an added flag, so it no
  longer matches the pinned command but still carries the owner prefix — is removed, and
  one whose command no longer carries the prefix at all is left alone and **named** in the
  result so the caller can say which entry it did not touch.

**Both sides:** the byte-exact restoration is proven able to fail against a build whose
removal span is off by the one comma the insertion added (the classic off-by-one in this
shape of edit), and proven to pass across the whole table. The delete-the-file decision is
proven both ways in the same run — it fires for the absent-file case and does not fire for
the operator-file case — because a flag that is always true and a flag that is always false
are indistinguishable from a correct one when only one case is tested.

**depends_on:** E2-L3-T4 · **verifies:** `dec-0008`

### E2-L3-T6 — Wire the CLI with `--local`, `--dir`, `--uninstall` and a confined root

Mirror `cli.ex:5141-5195`. `--dir <path>` wins; otherwise `--local` selects
`<cwd>/.claude/settings.local.json` and the default is `~/.claude/settings.json`. The
committed `.claude/settings.json` of a project is **never** a target — in a public repo
that publishes the operator's workflow (kazi's ADR-0034, and this repo's own rule that
every repo is potentially public).

The root is opened as an `*os.Root` and every name below it is relative, so `..` and an
escaping symlink are refused by the operating system. **Reuse `openClaudeRoot` and
`claudeRoot` from `cmd/dira/install_skill.go`** rather than declaring a second pair in the
same package; `claudeRoot` gains a `Remove` method for T5's deletion decision, and the
`skill.Root` interface is left alone (adding a method to it would force
`internal/skill` to grow a capability it does not need). `path/filepath` stays out of
`cmd/dira` — `dec-0005`'s allowlist grants it `os` and nothing else.

Exit status follows `docs/lore.md` L-0020 and `install-skill`'s precedent: **0** whenever
the command ran, including `UNCHANGED` and including a refusal to touch an edited entry;
**1** when dira could not do the work (unreadable file, malformed JSON, failed write);
**2** when the caller mistyped. Output lines follow `.agents/product-marketing.md` §10:
name the path, say what happens next, say how to revert.

**Files:** `cmd/dira/install_hooks.go`, `cmd/dira/install_hooks_test.go`,
`cmd/dira/main.go` (the one registry line in `newApp` only)

**acc:** `go test ./cmd/dira -run 'TestInstallHooksCommand|TestHelpNamesEveryRegisteredCommand|TestCommandNamesAreUnique'`
passes, against an injected temp root so no test ever touches a real `~/.claude`:

- a first install writes the user-level file under the injected root, prints `INSTALLED`
  and the path, and exits 0; a second prints `UNCHANGED` and exits 0 with the file's
  sha256 unchanged;
- `--local` creates `<dir>/.claude/settings.local.json`, and the test **fails if
  `<dir>/.claude/settings.json` exists afterwards** — the committed file is the one thing
  this command may never create;
- `--dir` overrides both; `--uninstall --local` targets the local file only;
- `--uninstall` after a fresh install into an absent file leaves **no file** on disk;
- every success path prints the exact `--uninstall` invocation that reverts what it just
  did, including the `--local` or `--dir` flag it was given, so the printed line is
  copy-pasteable rather than approximately right;
- a malformed target file exits **1** with one line on stderr and writes nothing; an
  unknown flag exits **2**; a refusal to remove an operator-edited entry exits **0** and
  names the entry;
- the whole suite is run with the injected root set to a temp path and **fails if anything
  under the real `$HOME` was created or modified during it**, asserted the way
  `TestInstallSkillCommandWritesNothingOutsideTheRoot` already does it;
- `go test ./internal/ledger -run TestNoFilesystemImportsAboveTheBackend` still passes with
  these files in place, and `internal/installhooks` has **not** been added to its allowlist;

**Both sides:** the `$HOME`-untouched assertion is proven able to fail by pointing the

### E2-L3-T7 — Assert every command string the installer wrote is accepted by the binary

Clause (f), and the reason it is in the lane's `acc:` line. It reads **the settings file
the installer actually wrote**, not the pinned table — a check against the table would
verify a declaration rather than a result, which is the line `docs/lore.md` L-0001 closes
on.

**A correction to the prompt's file assignment, stated rather than silently applied.** The
prompt puts this whole test at `internal/installhooks/commands_test.go`. The acceptance
half cannot live there: the command registry is `newApp(...).commands` in
`cmd/dira/main.go`, unexported and in package `main`, so no `internal/` package can
enumerate it — the identical correction E2-L2-T5 made and recorded. So the **parser** is
`internal/installhooks/command.go` with its unit tests in `internal/installhooks`, and the
**assertion against the real registry** is `cmd/dira/install_hooks_commands_test.go`, in
package `main`. That file **reuses `probeFlag`, `commandNames`, `notAFlag` and
`unknownFlagReport` from `cmd/dira/skill_covers_test.go`** — they already exist in this
package and do exactly this job. The lane's `acc:` names the package that must pass; this
adds one, and removes nothing.

**Files:** `internal/installhooks/command.go`, `internal/installhooks/command_test.go`,
`cmd/dira/install_hooks_commands_test.go`

**acc:** `go test ./internal/installhooks -run TestParseHookCommand` and
`go test ./cmd/dira -run TestWrittenCommandsAreReal` both pass:

- the parser takes an installed command string, asserts the shell guard
  `2>/dev/null || true` is present, strips it, and returns the verb and the flag names.
  It reports anything it cannot tokenise rather than guessing — an unbalanced quote is a
  broken command whoever reads it — and it returns an error, never an empty result, for a
  string that does not begin with `dira`;
- `TestWrittenCommandsAreReal` installs into a temp root, **parses the file that was
  written**, and for each of the three commands resolves the verb against
  `commandNames()` and each flag against `probeFlag(verb, name)`, failing with the
  **event name** and the offending token, not merely "a command was wrong";
- the test fails if fewer than three commands were extracted from the written file. An
  extractor that finds nothing satisfies "every extracted command resolves" and looks
  identical to a clean run — the exact shape of the five rule-1 instances L-0001 lists;
- `dira brief --context --chain` is among the three and passes, which is what keeps E1-L5's
  `--chain` commitment honest. **If it ever fails, report the contradiction — do not drop
  `--chain` from the example file to make this green.** A hook whose flag the binary
  rejects fails open and silently never briefs, which is the failure this clause exists to
  catch and which looks exactly like success.

**Both sides:** red is proven by splicing a bogus flag (`--e2-l3-t7-no-such-flag`) and a

### E2-L3-T8 — Prove the installed strings fail open, with the failure path observed firing

The epic's third clause: a non-zero `dira` exit must never block a session. The property
lives in the **installed string**, in `2>/dev/null || true`, so this test runs that string
through a real shell rather than calling any Go function.

**This is the task most at risk of proving nothing.** A fake `dira` that exits 0, or a
`sh -c` that never reached the fake because the real binary was found on `PATH` first,
produces a green test that certifies nothing at all. Every clause below therefore carries
the observation that the failure actually fired.

**Files:** `internal/installhooks/failopen_test.go`,
`internal/installhooks/testdata/fakedira/`

**acc:** `go test ./internal/installhooks -run TestFailOpen` passes:

- **the control, asserted first:** with the fake on `PATH`, running the command string
  with the `2>/dev/null || true` guard **removed** exits **non-zero**. If this passes, the
  test fails immediately — the failure path did not fire and nothing below is evidence.
  This is asserted per fake and per command string, not once;
- with a fake `dira` exiting 1, each of the three installed command strings executed via
  `sh -c` exits **0**;
- the same holds for a fake writing a line to stderr and exiting 2, and the outer stderr is
  **empty** — that is `2>/dev/null` doing its job;
- the same holds for a fake killed by a signal (`kill -SEGV $$`), which is the "it
  panicked" case and which `|| true` catches because the shell sees a non-zero status;
- the same holds for **no `dira` on `PATH` at all** — a `PATH` set to an empty temp
  directory. This is the likeliest real failure (hooks installed, binary later moved or
  upgraded), `sh` exits 127, and the guard neutralises it;
- **stdout is deliberately not suppressed, and that is asserted as the contract rather
  than tested as a leak:** a fake writing to stdout has that stdout reach the caller,
  because stdout is the product — it is the brief `SessionStart` injects and the staged
  count `Stop` reports. Only stderr and the exit status are neutralised. An `acc:` demanding
  silent stdout would be demanding a guard the shipped string does not contain and must not
  grow;
- **a hang is out of `|| true`'s reach and this test says so rather than pretending
  otherwise.** The shell guard cannot bound a `dira` that never returns; only Claude Code's
  own `timeout` can. So this asserts the timeouts **from the file the installer wrote**:
  `PreCompact` ≤ 60, `Stop` ≤ 10, `SessionStart` ≤ 5, each present and positive;
- the test fails if any command string read from the written file lacks `|| true`, and
  fails if it read fewer than three command strings.

**Both sides:** every clause above already carries its red control in the first bullet —
the unguarded string must fail for the guarded string's success to mean anything. The green
side is the untouched installed strings against every fake. The `PATH` isolation is itself
proven: before the fakes are used, the test runs bare `dira` under the prepared `PATH` and
asserts it resolves to the fake (by its output), so a machine with a real `dira` installed
cannot turn this suite green for the wrong reason.

**depends_on:** E2-L3-T6 · **verifies:** `dec-0008`, `int-0002`

## Two `acc:` readings settled here rather than left ambiguous

Neither is a weakening. Both are places where the lane's `acc:` line admits a reading that
cannot be satisfied, and the resolution is recorded because
`docs/plan/lanes/E2.md` records that this epic has already had one `acc:` found unpassable
as scheduled and corrected in writing rather than silently.

**Clause (c): "deletes the file if and only if install created it."** Taken literally and
without its scope, this cannot be implemented: nothing in a settings file records who
created it, and an install-created file that the operator has since edited must *not* be
deleted. The clause's own words — *"`--uninstall` immediately after a fresh install"* —
supply the scope, and under it the iff holds exactly. The implementable rule, which is
kazi's, is **delete iff the bytes still equal what a fresh install produces**; within the
clause's scope the two rules agree, and outside it the byte rule is the one that protects
the operator. T5 asserts both the scoped iff and the out-of-scope non-deletion, so the
distinction is tested rather than argued.

**Clause (g) and the prompt's "prints nothing to stdout or stderr."** The installed strings
redirect stderr and neutralise the exit status; they do not redirect stdout, and they must
not, because stdout is the payload — the brief that `SessionStart` injects into context.
Read as "the guarded string prints nothing on stdout under a failing dira", the clause is
satisfiable only by a fake that prints nothing, which is a fake that proves nothing. T8
therefore asserts the property the shipped string actually has (exit status neutralised,
stderr suppressed, stdout passed through) and adds the control the clause was reaching for:
the unguarded string must be observed exiting non-zero, or the guarded string's exit 0 is
not evidence of anything.

## What is already known, so no task re-derives it

**The two named corpora, pinned, from `qst-0003`'s neutrality run
(`docs/decisions-pending/qst-0003-neutrality.md` §1 and §3).** Both were shallow-cloned
read-only, forked/starred/interacted-with nothing:

| corpus | commit | documents | with ≥1 reasoned rejected alternative | alternatives extracted |
|---|---|---|---|---|
| **bbc/tams** | `8cd1ca536322ce0941e58d2c67210b2c7cd3ee80` | **49** | **44 (90%)** | **237** |
| **nulib/meadow** | `10f6ac2cb3f3c4e2894c4cf5dbed67544516faf1` | **31** | **0 (0%)** | **0** |

These four numbers per corpus (49/44/237 and 31/0/0) are `dec-0028`'s own dry-run example
text verbatim — the entry's "what the dry run must say" section is bbc/tams's and
nulib/meadow's real measured output, not an illustration. T2's `acc:` pins them literally
for that reason: a task whose extractor produces different numbers on the named corpora
has not implemented `dec-0028`, whatever else it does correctly.

**The extractor is corpus-agnostic by necessity, not by choice — the experiment already
paid for this the hard way.** `qst-0003-neutrality.md` §2 found the first (kazi-shaped)
extractor false-negatived on MADR, because MADR splits an option's *name* (under
`## Considered Options`) from its *reason* (under a separate
`## Pros and Cons of the Options`, as `* Bad, because …` bullets). The corpus-agnostic
successor (`extract2.py`, never committed — session scratchpad only, per §7) handles four
shapes and is the reference this lane ports:

1. inline-reason bullets (kazi's own house style — option and reason in one bullet),
2. sub-heading-per-option with prose reasons underneath (Sylius),
3. names-here-reasons-elsewhere — the MADR join (bbc/tams),
4. no alternatives section at all (nulib/meadow, IRS partially).

**Three specific bugs the experiment found and fixed, named because a reimplementation
that skips the controls will rediscover them** (§2 "Three bugs the controls and
hand-reading caught"):

- an `### Option N: …` heading *inside* the Pros-and-Cons block was itself treated as a
  new alternatives section, inflating one MADR reason into six;
- `Option 1: Assume DELETE requests will be mediated by other systems` was split at the
  first colon, turning the option into the bare string `Option 1` and its descriptive
  name into the "reason" — this alone inflated tams' unmatchable-label rate 20-fold;
- IRS sub-sub-headings inside an option's own body (`#### Branches`, `##### Error
  workflow`) were counted as options.

T2's `acc:` carries a regression fixture for each.

**Seven controls, six from the experiment plus one this lane adds.** From §2's table,
each with its validated expected answer:

| control | contents | expected |
|---|---|---|
| `0001-bare-names` | 5 options, names only | 5 bare, 0 reasoned |
| `0002-thin-reasons` | 3 options, label-length reasons ("too slow") | 3 thin, 0 reasoned |
| `0003-rich-with-revisit` | 3 options, full grounds + revisit conditions | 3 reasoned, 3 carrying `revisit_if` |
| `0004-no-section` | no alternatives heading anywhere | 0 |
| `c5-madr-reasons-elsewhere` | MADR: bare option list, reasons in a separate Pros-and-Cons block | 1 reasoned — proves the cross-section join works and the *chosen* option is correctly excluded |
| `c6-madr-no-reasons` | MADR: bare option list, **no** Pros-and-Cons block | 2 bare — proves C5 is a real join and not a join that fabricates a reason for everything |
| `c7-terse-labels` *(new)* | 5 options, ≥3 of them ≤2 words (`Go`, `Rust`, `Redis`-shaped) | median option-label length ≤2 words, label-expansion flagged NEEDED |

C5/C6 is the pair that matters per the source report: "without C6, a join that returned a
reason for everything would look identical to a working one" — T2's `acc:` keeps that
pairing.

**The label-expansion repair is conditional, not universal, and the evidence for that is
already measured** (`qst-0003-neutrality.md` §4): unmatchable (≤2-word) option labels ran
6% (kazi), 1% (tams), 0% (Sylius), 8% (IRS) — kazi's terseness is house style, not a
property of ADRs. Neither named corpus needs the repair (tams 1%, meadow has no
alternatives to have labels at all), so `c7-terse-labels` is what proves the repair can
fire at all; both named corpora are what prove it does not fire when it should not.

**The tier, hook and state an imported entry carries, settled here rather than invented
per-task.** `source.hook: import` already exists in `schema/entry.schema.json`'s enum —
this lane was anticipated, not improvised. `source.tier` is closed at
`regex | semantic | human` (`dec-0003`), and this extraction is structural pattern
matching over already-written text with no model in the loop — the same shape as `dira
sniff`, not a live session. So it is `tier: regex`. `dec-0003` states regex-tier output "is
written with `state: staged` … never accepted, because a regex has no business asserting
rationale," without carving out an exception for import. Taking that literally rather than
inventing a `tier: human` fiction for machine-copied text means **imported entries land in
the ledger as `staged`, `source.tier: regex`, `source.hook: import`, and flow through
E2-L4's existing `dira distill` for individual disposition** — this lane does not build a
second confirm/accept path. "Imports on confirmation" (the exit criterion's phrase) means
the *corpus-level* dry-run confirmation writes the batch to the ledger; it is not a claim
that each of the 44 tams entries is `accepted` the moment it lands. This also keeps a
44-entry staged queue inside the shape `qst-0003` already validated as finishable (kazi's
own 63-item queue).

**The index artifact's home, settled rather than left to the implementer to invent.**
`internal/index` is the existing SQLite read cache over *ledger entries* (E1-L3) — reusing
its name or its table for arbitrary external documents would be the exact "two lanes
declared the same identifier" hazard `docs/plan.md`'s Parallel Work section warns about.
Indexed-not-imported documents are not ledger entries (`cst-0002` is closed; there is no
kind for "a document dira can point at but not enforce") and must never be written under
`.dira/entries/`. `.dira/config.toml`'s own comment states the only two homes that exist:
"Everything under `entries/` is written by dira itself … and everything under `cache/` is
derived and gitignored." An index artifact is exactly that — regenerable by re-running
`dira import` over the same directory — so it lands under `.dira/cache/imports/`, never
committed, never confused with `internal/index`'s database.

**The zero/nonzero threshold is the literal one `dec-0028` states, and the untested middle
band is out of scope, flagged rather than silently decided.** `dec-0028`'s own words are
"offers indexing when the yield is nothing" — read literally: `INDEX` iff zero documents
carry a reasoned rejected alternative, `IMPORT` otherwise. `qst-0003-neutrality.md` §6
lists "a corpus in the 20-60% band" as what would still change this answer and states
outright that "whether the middle is populated decides whether the dry-run's advice is a
clean binary or a judgement call" — unmeasured. This lane's two named corpora sit at the
extremes (0% and 90%) precisely because those are the only two the exit criterion names.
A corpus at, say, 35% is not this lane's to resolve.

**What this lane does not own.** `dira why` citing an indexed (not imported) document is
`dec-0028`'s own future-tense claim ("so `dira why` can cite them") and is not built here —
this lane writes the artifact `dira why` would need, nothing reads it yet. Disposing of the
44 staged tams entries is `dira distill`, already built in E2-L4. The ADR mirror
(`dec-0009`) fires on *accepting* a staged decision, which is E2-L4's confirm transition,
not this lane's write path — an imported entry gets no ADR until a human accepts it through
the existing flow. A corpus in the untested middle band is flagged above, not absorbed.

### E2-L7-T6 — Wire `dira import <dir>`: confirmation, the real writes, idempotence

The first command in this repository to read a directory the user names rather than one
dira owns. `<dir>` is walked with `os.ReadDir`; `cmd/dira` needs `path/filepath` to join
names while walking, which its `internal/ledger/boundary_test.go` allowlist entry
currently does not grant (`{"os"}` only) — widen it to `{"os", "path/filepath"}`, named in
the diff as `docs/lore.md`'s own boundary-test comment asks ("adding one is a design
decision, and it should read like one in the diff"). `internal/importadr` itself imports
neither; every function in it still takes bytes or the structured output of another
function in the package.

Default behaviour: print T3's report, read one line from stdin, confirm on `y`/`yes`
(case-insensitive), decline otherwise. `--yes` skips the prompt and confirms
unconditionally, for scripted use.

**Files:** `cmd/dira/import.go`, `cmd/dira/import_test.go`,
`cmd/dira/main.go` (the one registry line), `internal/ledger/boundary_test.go` (widen the
existing `cmd/dira` entry only)

**acc:** `go test ./cmd/dira -run 'TestImportCommand|TestNoFilesystemImportsAboveTheBackend|TestHelpNamesEveryRegisteredCommand|TestCommandNamesAreUnique'`
passes, against an injected temp `.dira/` so no test ever touches this repo's own ledger:

- run against T1's meadow fixture with stdin `y`, it writes **zero** files under
  `.dira/entries/` and **exactly one** file under `.dira/cache/imports/`; with stdin `n`,
  it writes nothing at all; both exit 0;
- run against T1's tams fixture with `--yes`, it writes **exactly 44** files under
  `.dira/entries/`, each validating against `schema/entry.schema.json`, and writes nothing

  `.dira/entries/` — the idempotence T5 proved at the data level, now observed at the real

- `go test ./internal/ledger -run TestNoFilesystemImportsAboveTheBackend` passes with

- `import` appears in `dira --help` because it is registered in `newApp(...).commands`,

**Both sides:** the confirmation-declined path is proven able to fail against a build that

### E4-L4-T2 — Grouping by `derives_from`, with the unparented group and count conservation

For every entry in the ledger, find its own `derives_from` edge (an entry declares this
on itself — no inbound lookup needed, unlike `DecisionBlocked`) and group it under that
target as a child. An entry with no `derives_from` edge is not dropped — it appears under
an explicit **unparented** group, because `kazi portfolio` groups by goal and would
simply omit anything ungrouped; the unparented group is the specific structural
difference this lane exists to add.

**Files:** `internal/cli/map.go` (same file, later wave), `internal/cli/map_test.go`

**acc:** `go test ./internal/cli -run TestMapGrouping` passes: a fixture ledger where
every entry carries a `derives_from` edge produces a tree with zero entries in the
unparented group; a fixture with one entry lacking `derives_from` produces exactly one
entry in an explicitly-labelled unparented group, distinguishable in the rendered output
from a parent with an empty child list; and — the count-conservation clause — for a
fixture combining both cases, the number of entries appearing **anywhere** in the
rendered tree (summed across every parent's children plus the unparented group) equals
the ledger's total entry count, asserted by a test that adds one more entry to the
fixture and checks the rendered total increments by exactly one, so the check cannot pass
by coincidence on a fixed fixture size.

**Both sides:** the count-conservation assertion is proven able to fail against a grouping
implementation that silently skips an entry whose `derives_from` target does not exist in
the ledger (a dangling edge — plausible, since `schema/entry.schema.json` does not enforce
that a `derives_from` target resolves) and is shown to under-count before the real
implementation, which routes a dangling-target entry into the unparented group rather than
dropping it, is shown to conserve the count.

**depends_on:** `E4-L4-T1` · **verifies:** `dec-0004`

### E4-L4-T3 — Per-intent roll-ups summed from children

Each parent's roll-up line is the sum of its own children's buckets, in the
`3 done · 1 running · 1 stuck`-shaped form §6.4 shows — read literally as counts per
bucket-label, not a fixed three-term string, since a parent with entries in more than
three of the six buckets must still show all of them.

**Files:** `internal/cli/map.go` (same file), `internal/cli/map_test.go`

**acc:** `go test ./internal/cli -run TestMapRollups` passes: a fixture parent with
children in exactly the buckets `{Completed, InProgress, ExecutionBlocked}` renders a
roll-up whose counts match `{converged: 1, "in progress": 1, "execution-blocked": 1}`
(using T4's committed labels); the roll-up **excludes** the unparented group (it has no
parent to roll up into) and excludes grandchildren — this lane groups one level only, so a
child that is itself a parent contributes to its *own* parent's roll-up as one unit, not
by flattening its own children upward, asserted by a three-generation fixture; and — the
mutation test the lane `acc:` line demands by name — flipping one child's bucket in the
fixture (achieved by re-running `Join`/`ToBePlanned` against a mutated ledger copy, not by
hand-editing the rendered string) changes the roll-up's count for the old bucket down by
one and the new bucket up by one, with every other parent's roll-up in the same fixture
unchanged.

**Both sides:** the mutation test **is** the two-sided proof by construction — before
mutation the roll-up reflects the original bucket, after mutation it reflects the new
one, and a roll-up computed once and cached (rather than derived fresh each render) would
fail the second half.

**depends_on:** `E4-L4-T2` · **verifies:** `dec-0004`

### E4-L4-T5 — The `--json` shape, documented and deterministic

`--json` emits dira's six bucket names — never kazi's five (`done|running|blocked|todo|planned`)
or three (`in_progress|stuck|complete`) — and is byte-identical across two runs on an
unchanged ledger once the single top-level `observed_at` field is removed from both
outputs before comparing.

**Files:** `internal/cli/json.go`, `internal/cli/json_test.go`,
`docs/design/schemas/map.md` (the documented shape — this lane's copy of the pattern
`docs/schemas/collective-result.md` uses on the kazi side, cited in `dec-0008`'s own
source comments)

**acc:** `go test ./internal/cli -run TestMapJSON` passes: every bucket value appearing
anywhere in `--json` output is one of the six `status.Bucket` string values, asserted by
decoding the output back into a struct and checking every bucket field against
`status.Buckets` — a test that fails if a raw kazi `RepoBucket`/`RowBucket` string ever
leaks through unmapped; running `dira map --json` twice in a row against an unchanged
fixture ledger and deleting each output's top-level `observed_at` field before comparing
yields byte-identical results, asserted via a real two-invocation subprocess test (not two
in-process calls sharing state that would trivially agree) so the determinism claim is
about the command, not about calling a pure function twice; and the documented shape file
is checked against the actual emitted JSON's key set by a test reading both, so the doc
cannot drift from the code silently (`docs/lore.md`'s dominant-finding pattern — a
declaration nobody checks against its result).

**Both sides:** the bucket-leak assertion is proven able to fail by constructing a
deliberately wrong encoder inline in the test that copies `kazi.RepoBucket` values
straight through without mapping them to `status.Bucket`, and shown to leak `"complete"`
(a `RepoBucket` value, never a `status.Bucket` one) into the output before the real
encoder is shown clean.

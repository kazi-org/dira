## What is already known, so no task re-derives it

**The version-injection path this lane must point goreleaser's `ldflags` at is
already built and tested, by E0-L1.** `cmd/dira/main.go:39` declares
`var version = "dev"`; `cmd/dira/build_test.go:233-236`
(`TestVersionIsSetByLdflags`) builds the real binary twice — plain, and with
`-ldflags "-X main.version=1.2.3"` — and asserts `dira --version` prints `dev` and
`1.2.3` respectively. Its own comment reads *"E0-L4's release pipeline depends on
this exact mechanism."* This lane's job is to point goreleaser at
`main.version=main.version`, on the module path `github.com/kazi-org/dira/cmd/dira`,
never to rebuild flag parsing.

**goreleaser's own `{{.Version}}` template variable already strips the tag's
leading `v`.** This is what makes "prints exactly `0.0.1-rc.1`" satisfiable by
`-ldflags "-X main.version={{.Version}}"` with no extra string surgery in the
workflow — goreleaser, not this lane's YAML, owns that stripping.

**`.gitignore` already accounts for goreleaser's default output.** Lines 13-14
ignore `/dira` and `/dist/` — goreleaser's default working directory is `dist/`, so
no task needs to touch `.gitignore`.

**CI already set the two conventions this lane's workflow must match, not
reinvent.** `.github/workflows/ci.yml` pins every `uses:` to a 40-character commit
SHA (e.g. `:79`, `:87`) and takes the Go toolchain from `go-version-file: go.mod`
rather than a literal (`:89`). `release.yml` follows both; a task that restates a
Go version in YAML or pins a floating tag is wrong by the repo's own established
gate, not just by kazi's precedent.

**`CGO_ENABLED=0` is already the codebase's de facto choice, one layer up.**
`go.mod` depends on `modernc.org/sqlite` (pure Go), not `mattn/go-sqlite3` — E1 has
already made the choice this lane's risk note predicts it will force. Nothing to do
here beyond noting it; the `.dira/` decision entry the lane's risk note asks for is
the maintainer's call, not a task in this file.

**goreleaser is not vendored and nothing in this repo installs it.** Same shape as
L-0017 (Playwright): a fresh clone has no `goreleaser` binary. Every task below that
needs to run it does so via `go run github.com/goreleaser/goreleaser/v2@<pinned
version> ...` rather than assuming a global install — this keeps the tool version
pinned and reproducible without adding it to `go.mod` (a `go run pkg@version`
invocation is not a module dependency and does not appear in `go list -deps
./cmd/dira`, so it cannot trip E0-L1's zero-third-party-dep clause).

**New test-only packages in this lane must carry no non-test `.go` file, or they
trip `dec-0005`'s boundary check on the first `go test ./...`.**
`internal/ledger/boundary_test.go`'s `moduleImports` (`:124-131`) runs
`go list -f ... github.com/kazi-org/dira/...` — **every** package in the module, not
only what `cmd/dira` reaches — and reads only `.Imports` (non-test files). A package
containing solely a `_test.go` file has no non-test imports to report and is
invisible to the check with zero allowlist edits, exactly how `internal/installhooks`'s
test files already import `os`/`os/exec` freely per `docs/plan/tasks/E2-L3.md`'s own
note. `internal/relbuild` and `internal/relwf` below are both structured this way —
one `_test.go`, no sibling implementation file — specifically so this lane never
needs to touch `internal/ledger/boundary_test.go`'s `allowed` map.

### E0-L4-T2 — Prove the snapshot build emits both targets with CGO_ENABLED=0 baked in

file — see the boundary note above)

**acc:** `go test ./internal/relbuild -run TestSnapshotBuildProducesBothTargets`
passes:

- `go run github.com/goreleaser/goreleaser/v2@<pinned> build --snapshot --clean -f
  .goreleaser.yaml` exits 0;
- exactly one built binary under `dist/` matches the darwin/arm64 target and exactly
  one matches linux/amd64 — located by walking `dist/` rather than a hardcoded path,
  since goreleaser's per-target subdirectory naming is an implementation detail of

  matching `--clean`'s contract).

darwin build only, rebuild, and observe `go version -m` no longer report

### E0-L4-T3 — Author `.github/workflows/release.yml` and its structural gate

**Files:** `.github/workflows/release.yml`, `internal/relwf/release_workflow_test.go`
(test-only package, no non-test `.go` file)

The workflow runs the smoke test *before* any publish step, on a native
Apple-Silicon runner (`macos-14` or newer — `macos-13` is Intel and cannot execute a
darwin-arm64 binary), because `CGO_ENABLED=0` makes cross-compiling both targets from
one runner free but does not make cross-*executing* them free. `permissions:
contents: write` is scoped to the one job that creates the Release, matching
E0-L3's own risk note about a workflow left at the default write scope.

**acc:** `go test ./internal/relwf -run TestReleaseWorkflowStructure` passes,
parsing `.github/workflows/release.yml` with `gopkg.in/yaml.v3`:

- `on` includes `push.tags` containing `v*`, a `workflow_call` with a required
  string input named `tag`, and a `workflow_dispatch` with the same;
- every step's `uses:` value matches a 40-character commit SHA after the `@`
  (`^[^@]+@[0-9a-f]{40}$` against the parsed scalar, which already excludes the
  trailing `# vX.Y.Z` YAML comment);
- the workflow carries **no top-level `permissions:` key**, and the job that
  creates the Release declares `permissions: contents: write` at job scope;
- the job that sets up Go uses `go-version-file: go.mod`, never a literal
  `go-version:`;
- within that job's step list, the first step whose `run:` contains `--version`
  (the smoke test) has a strictly lower array index than the first step that
  creates or uploads a Release — asserted by index, not by string search, so
  reordering the steps trips it rather than a search finding both anywhere in the
  file.

**Both sides:** the SHA-pin assertion is proven able to fail against a copy of the
file with one `uses:` reverted to `@v5`, and proven to pass on the real file. The
step-ordering assertion is proven able to fail against a copy with the smoke-test
step moved after the publish step.

**Files:** none new. This task pushes tag `v0.0.1-rc.1` to `kazi-org/dira`,
observes, and deletes both the tag and the Release it produced — cleanup, not
history, per the lane's own instruction that the task creating a disposable tag
owns removing it.

**acc:** all of the following, observed in one run against a commit carrying T1-T3:

- `gh run list --workflow=release.yml` (or the API equivalent) shows the run
  triggered by the tag push finish with conclusion `success`;
- `gh release view v0.0.1-rc.1` lists three assets: a darwin-arm64 archive, a
  linux-amd64 archive, and a checksums file;
- each of the three asset URLs returns HTTP 200 to an unauthenticated `curl -I`;
- extracting the darwin-arm64 archive and running the contained `dira --version`
  prints exactly `0.0.1-rc.1` — no leading `v`, nothing else on the line;
- the tag and Release are then deleted (`gh release delete v0.0.1-rc.1`,
  `git push origin :refs/tags/v0.0.1-rc.1`), and the task's completion note records
  the run id and commit SHA it verified against.

**Both sides:** before trusting a green run, the same tag is pushed once against a
commit where T3's smoke-test step is deliberately given a wrong expected-version
string, and the run is observed to fail **at the smoke-test step**, not merely
somewhere. Only after that red is observed does the real run above count as
evidence — otherwise a workflow that skips its own smoke test and a workflow that

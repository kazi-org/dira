## What is already known, so no task re-derives it

**Point 11 of `docs/plan/lanes/E4.md`'s "What I verified myself" is why this lane's
`acc:` line is worded the way it is, quoted here because every task below is designed
against it:** `schema/entry.schema.json` is `additionalProperties: false` with a closed
`properties` list and a `state` enum carrying no execution value, and E0 already wires
that validator as a test. So "grep entry files for a status field" is near-vacuous —
green before this lane starts. **This lane's job is what the schema cannot catch:**
status smuggled into `tags`, into an edge `note`, or asserted by a package that can
write. Point 10 (`kazi` exits 0 on success and 2 on a bad argument, printing help to
**stdout** either way) is why T1's stubs each reproduce a specific real failure mode
rather than one generic "kazi is broken" stand-in.

**Every clause in this lane is two-sided by the lane's own written standard, restated
here because it is the thing every task below is graded on:** *"An absence assertion
alone is worthless... a lint passes when its pattern list is empty."* Each task's `acc:`
therefore pairs an absence/refusal assertion with something that must make the same check
**fail** — a poisoned fixture, an injected label, a mutated file.

**The exact vocabulary list T4's lint scans for, recorded here rather than left implicit
— a lint with an implicit list is unauditable, per the lane's own risk note.** Drawn from
`internal/kazi`'s raw status/bucket strings (E4-L1) and `internal/cli`'s committed CLI
labels (E4-L4-T4), matched case-insensitively as whole phrases against `tags` values and
edge `note` text:

```
converged
in progress / in_progress
execution-blocked / execution_blocked
over_budget / over-budget
terminated
stuck
```

**Deliberately excluded: bare `blocked` / `blocks`.** `blocks` is itself a legitimate
edge **type** name (`schema/entry.schema.json`'s `EdgeBlocks`) and an ordinary English
word that appears in legitimate edge notes describing *why* one entry gates another (e.g.
`qst-0005`'s own note: *"disposition capture has no automatic path until the hook
exists"* — and its body, not scanned by this lint, says *"blocks nothing"*). Linting on
the bare word would false-positive on the ledger's own structural vocabulary, which is
exactly the false-alarm failure mode a near-vacuous check produces from the other
direction. The list above is deliberately the *execution-status-specific* phrases only.

**The read-only-mount substitution, recorded as a design choice this lane makes rather
than assumed.** A literal bind-mounted read-only filesystem needs root or container
privileges most CI runners (and this worktree's own sandbox) do not have. T3 instead
`os.Chmod`s every file and directory under a copy of `.dira/` to mode `0555` before
running `dira map` against it — removing write permission is the property the acc: line's
"mounted read-only" clause is actually testing (a write attempt fails), and it is
achievable everywhere `go test` runs. This is recorded here, not silently substituted,
per the honesty rule.

### E4-L5-T1 — The stub-kazi matrix: five reasons, five distinct rendered lines

Run `dira map` (the real command, via `os/exec` from the test — this is the one place in
this lane that shells a binary, and it is dira's own, never kazi's) against each of
E4-L1-T7's five fake-`kazi` scripts placed alone on an injected `PATH`, plus a sixth

**Files:** `test/acceptance/degradation_test.go`, reusing
`internal/kazi/testdata/fakekazi/` (E4-L1-T7) rather than recording a second set —
**acc:** asserts the two directories' fake count matches, so a fake added to one and not
the other is caught.

**acc:** `go test ./test/acceptance -run TestDegradation` passes: for each of the five
failing fakes, `dira map` exits **0**; stdout renders every ledger-side bucket
(`to be planned`, `planned`, `blocks this`, and the two terminal groups) for a fixture

observed across the five fakes are pairwise **distinct** strings (reusing E4-L1-T7's own
distinctness proof, now observed at the CLI's rendered output rather than at
`internal/kazi`'s typed value — a different layer, so this is not a duplicate test); and
against the sixth, succeeding fake, `dira map` prints **no** unavailability line at all —
the explicit positive control proving the five negative cases are not simply "always

**Both sides:** the "no banner on success" clause is proven able to fail against a

### E4-L5-T3 — The no-write proof

`dira map` never writes to `.dira/`, proved two ways: byte-identical hashes across a run,
and a successful run against a copy with write permission removed.

**Files:** `test/acceptance/nowrite_test.go`

**acc:** `go test ./test/acceptance -run TestNeverStored` passes: sha256 of every file
under a fixture `.dira/` is computed, `dira map` (and `dira map --json`) is run against
it, and every file's sha256 is recomputed and compared equal, file by file — a test that
fails if the file **set** changes too (a new file appearing, or one disappearing, both
checked independently of the hash comparison); the same fixture is copied, every file and
directory under the copy is `chmod`ed to `0555` (this lane's recorded substitute for a
read-only mount, per "What is already known" above), and `dira map` against the read-only
copy still exits **0** and renders the same content as the writable copy; and — the
mutation control the lane's own standard demands — a deliberately wrong test-only shim
that writes one byte to one entry file mid-run (not committed to `internal/cli` or
`cmd/dira`; constructed inline in this test as a stand-in for a regression) is shown to
change that file's sha256, proving the hash comparison would in fact catch a write if
`dira map` ever made one.

**Both sides:** the mutation control above **is** the red side — without it, a
comparison that (by a bug) always reports "unchanged" regardless of input would pass
every clause of this task vacuously, which is rule 1's exact shape from `docs/lore.md`
L-0001.

**depends_on:** `E4-L4` · **verifies:** `dec-0004`, `int-0003`

list fixed in "What is already known" above. This is the check the entry schema cannot
make (point 11): a status word in `tags` or a `note` validates cleanly against

**Files:** `internal/lint/vocabulary.go` (a small standalone checker, reusable outside

— see `docs/plan/tasks/E2-L3.md`'s precedent note on that shape), `internal/lint/vocabulary_test.go`,
`test/acceptance/vocabulary_test.go` (wiring the lint over the real fixture ledgers this
epic already built: E4-L2's `testdata/ledgers/` and E4-L4's golden-file fixtures)

**acc:** `go test ./internal/lint -run TestVocabularyLint` and `go test ./test/acceptance
-run TestNeverStored` (the lint is folded into the same named suite as T3, since both
prove the same invariant from different angles, matching the lane's single locked test
command) both pass: every entry under E4-L1 through E4-L4's committed fixture ledgers
finds **zero** matches, asserted per fixture directory so a match in any one is
attributable; a **deliberately poisoned** fixture — a copy of one real fixture with one
entry's `tags` list gaining `"execution-blocked"`, and a second poisoned copy with one

**not** to match, proving the lint targets ledger-file content, not a legitimately-labelled

**Both sides:** the "zero matches on real fixtures" clause and the "at least one match on
poisoned fixtures" clause are each other's control — a lint with an empty phrase list
would pass the first and fail the second, which is exactly the failure the lane's standard
names by name ("a lint passes when its pattern list is empty").

### E4-L5-T5 — The structural write-barrier

**A resolved reading of the locked `acc:` line's phrase "the map command's package graph
does not import the ledger writer package," recorded here rather than left ambiguous —
the same kind of settled reading `docs/plan/tasks/E2-L3.md`'s closing section records for
its own lane, and `docs/plan/tasks/E4-L4.md`'s label table records for its own.** Taken
completely literally this cannot hold: `cmd/dira/map.go` (E4-L4-T1) must construct a
concrete `ledger.Store` to open the real ledger for reading at all, and
`internal/ledger/local` is the **only** concrete `Store` implementation in this repo
(`dec-0005`) — it does not separate a read-only sub-package from `Create`/`Put`/`Delete`.
Every existing command that reads the ledger (`brief`, `why`, `check`, `ui`) imports
`internal/ledger/local` in its `cmd/dira/*.go` wrapper for exactly this reason (verified:
`grep -l 'ledger/local"' cmd/dira/*.go` lists `brief.go`, `reindex.go`, `check.go`,
`ledger.go`, `why.go`, `ui.go` — every read-only command among them). The clause's
implementable reading, and the one this task enforces: **`internal/cli`, `internal/status`
and `internal/kazi` — the packages that hold `dira map`'s derivation and rendering logic
— never import `internal/ledger/local`.** Only `cmd/dira/map.go`, the thin wrapper that
already holds write-capable filesystem access by construction (the same shape
`cmd/dira/brief.go` already has), is exempted, mirroring the boundary
`internal/ledger/boundary_test.go` already draws around `cmd/dira` for `os`.

**Files:** `internal/cli/boundary_test.go`

**acc:** `go test ./internal/cli -run TestNoLedgerWriter` passes: `go list -deps
./internal/cli`, `go list -deps ./internal/status` and `go list -deps ./internal/kazi`
(all three, not just the one the lane's command names, since the join and the kazi client
are equally upstream of anything that could smuggle a write) each exclude
`github.com/kazi-org/dira/internal/ledger/local` from their output; and `cmd/dira`'s own
import of `internal/ledger/local` is asserted **present** (a positive control proving the
`go list` mechanism actually reports imports it should find, rather than a broken
invocation that reports nothing for everything).

**Both sides:** the exclusion assertion is proven able to fail by a throwaway import added
to a scratch copy of `internal/cli` (not committed, the same "checked but not landed"
convention `docs/plan/tasks/E4-L2.md`'s T6 uses for its own `go list -deps` control) and
shown to be caught, mirroring `internal/ledger/boundary_test.go`'s own self-test
precedent.

### E4-L5-T6 — Wire the named suite into CI

`.github/workflows/ci.yml`'s existing `go test -race -count=1 -v ./...` step
(`ci.yml:106-118`) already sweeps every package this lane adds — it is a whole-module
run, and its own non-zero-count guard (*"go test executed 0 tests. A green run over an
empty suite is not a gate"*) already fires if the **entire** suite goes empty. What it
does **not** catch is this lane's two named tests specifically disappearing while the
rest of the module's tests keep the global count non-zero — a renamed or accidentally
`t.Skip()`-ed `TestDegradation` would sail through today's check. This task adds the
named-suite assertion the lane `acc:` line's own wording ("this named suite ran and
passed N tests") requires, extending the existing step rather than duplicating a second
`go test` invocation.

**Files:** `.github/workflows/ci.yml` (extends the existing "go test -race" step; adds no
new job)

**acc:** the CI run (inspected via `gh run view` after a push, or `act`/a local run of the
same script for pre-merge verification) shows a step that greps `${RUNNER_TEMP}/gotest.log`
(the same log the existing step already writes at `ci.yml:110`) for `=== RUN
.*TestDegradation` and `=== RUN .*TestNeverStored`, counts each, and fails the step with a
named `::error::` message if either count is zero — mirroring the existing step's own
`ran -eq 0` pattern at `ci.yml:115-118` rather than inventing a new idiom; and a **local**
run of the same script against a deliberately renamed copy of `TestDegradation` (renamed
in a scratch branch used only to observe this, not committed) is confirmed to trip the new
check before the real, correctly-named suite is confirmed to pass it — since this task
cannot itself force a red CI run without committing a broken test, the both-sides proof is
recorded as an observation made once locally, named in the PR body rather than replayed
as an automated test.

**Both sides:** as stated above — the negative observation is manual and one-time by
necessity (CI infrastructure changes are graded on the actual CI run, not a nested test of
the workflow file), and this is recorded honestly rather than dressed up as an automated
gate it is not.

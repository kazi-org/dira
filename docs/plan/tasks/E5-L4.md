## What is already true, so no task re-derives it

- **The token-budget mechanism this lane's chain content must obey already exists,
  and today's `--chain` output does not go through it.** `internal/brief/render.go`'s
  `compose` spends a per-section token budget against `opts.MaxTokens`
  (`spent+cost > opts.MaxTokens`, `render.go:49`) and names what it dropped in a
  footer citing `cst-0001` (`render.go:294-313`). `chainNotice`'s block, by contrast,
  is appended unconditionally after that loop (`render.go:174-179`) — it costs
  nothing today because it is one fixed sentence, but a real chain render with content
  from two ancestor ledgers cannot stay outside the budget loop without silently
  breaking cst-0001 the moment it is added. T1 moves chain content **into** the same
  accounting, not beside it.
- **`chainNotice`'s doc comment is already known to be stale and this lane is where it
  gets fixed, not somewhere else.** `internal/brief/render.go:194-196`: "Tier
  resolution is E5 and is blocked on qst-0001... so this flag has to be a defined
  degradation." `qst-0001` is answered (`dec-0011`); T1 replaces both the code and
  this comment together, so the comment never again claims a blocked state that the
  ledger does not.
- **The resolution and the chain walk are E5-L2's, not this lane's to rebuild.**
  `chain.Walk` (`docs/plan/tasks/E5-L2.md`, T1) already returns, for a ledger's full
  parent chain, each ancestor's `Store` (or `nil` + why not) and its `Tier`. This
  lane's job is turning that into brief content — which entries to pull from each
  ancestor and how to spend the shared budget on them — not opening ledgers.
- **`cst-0001`'s ceiling is unconditional, including for the chain.** The lane's own
  entries line says so: "the token ceiling applies to the *chain*, not just the local
  brief." There is no flag that raises it, matching `internal/brief`'s existing
  comment that a raise "requires superseding the constraint in writing."

brief already spends, naming what it dropped rather than silently cutting it.

`internal/brief/brief.go` (the `Chain`/`Parents` doc comments only),

`go test ./cmd/dira -run TestBriefChain` both pass, against a fixture repo declaring

### E5-L4-T2 — Twelve active intents render as twelve, with the cap as a warning, never a truncation

`dec-0006`: "a personal ledger holding twelve active intents *is* the absence of
clarity, rendered legibly. dira's job there is to show that, not to fix it." A
brief that pages, truncates, or summarises past some count deletes the only signal
the cap exists to produce.

**Files:** `internal/brief/render_test.go` (extends T1's file; no new production code
is expected — this task is the proof that T1's renderer does not, even by omission,
introduce a limit) plus, only if T1's implementation needs one, a small
`internal/brief/cap.go` naming the warning threshold from `docs/design.md` §8
("three to seven of them and never more" is the *idiomatic* range, not an enforced
ceiling — the ledger holding twelve is the drift case the warning names, and nothing
in this lane may reject or hide the thirteenth entry to enforce the idiom).

**acc:** `go test ./internal/brief -run TestNoIntentCap` passes:

- a workspace-tier ancestor fixture holding 12 distinct active intents, each with a
  distinctive id-bearing string, produces a chain render containing **all 12** —
  asserted by searching for each of the 12 distinct strings individually and failing
  by name on the first one missing, not by counting lines (a renderer that merged two
  intents onto one line would pass a bare line-count check);
- the render additionally contains one warning line naming the count (`12`) and the
  ledger's own idiomatic range, asserted by a distinctive warning-marker string
  distinct from any per-intent line;
- raising the fixture to 20 active intents still renders all 20 by the same
  per-string search — proving the 12-case was not a coincidental threshold;
- this whole clause is asserted **inside** T1's ≤1500-token budget check too: a build
  is exercised where the budget is deliberately set low enough that 12 full intent
  lines cannot fit, and the render is shown to **drop entries and say so in the
  footer** (T1's `omitted` mechanism) rather than silently keeping all 12 by shrinking
  each line below legibility — cst-0001's ceiling and dec-0006's no-truncation rule
  both hold, and where they would conflict (more active intents than the ceiling can
  name), the ceiling wins and says what it cut, exactly as it already does for the
  local ledger.

**Both sides:** the "all 12, not paginated" clause is proven able to fail against a
version of the renderer capped at, say, 7 entries with a "+5 more" line — exercised in
a subtest and shown to fail the per-string search on the missing five — before the
real, uncapped renderer is shown to pass it.

**depends_on:** E5-L4-T1 · **verifies:** `dec-0006` (the cap is the clarity, not a
limit to enforce)

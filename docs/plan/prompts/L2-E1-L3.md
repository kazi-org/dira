# L2-E1-L3 — Make the SQLite cache derived and disposable, rebuilt by `dira reindex`

You are an L2 planner. Your job is to turn **one lane** into **tasks**, and nothing
else. **Write no Go code.**

## Context

**Epic:** E1 — the ledger (`docs/plan/lanes/E1.md`), roadmap M1.
**Lane:** `E1-L3`. **depends_on:** `E1-L1` (the storage interface, the entry codec,
the 200-entry fixture). `E1-L4` (`dira why`) and `E1-L5` (`dira brief`) both depend on
you, so the query API you plan is a contract two other lanes consume — define it
before they need it, and keep it small.

**Lane `acc:` verbatim:**

> the full read-path test suite runs twice against the 200-entry fixture — once
> cache-warm, once with `.dira/cache/` deleted before every query — and both runs
> produce byte-identical output for every query; `dira reindex` after deleting
> `.dira/cache/` reproduces a byte-identical cache-derived query result; editing an
> entry file so it disagrees with an existing cache makes every query return the
> **file's** value without a manual reindex; `git check-ignore .dira/cache/index.db`
> exits 0 in a test; and a read-only or unwritable `.dira/cache/` directory degrades
> to direct-from-files answers with a stated notice and exit 0, never an error.

**What this lane is for.** SQLite is in the design **only** as a derived read cache
under `.dira/cache/`, gitignored and rebuildable at any time (`dec-0002`). The
property that matters is not speed — it is that *the files win*. A design in which
the cache can be authoritative is a defect, because a stale row that outlives the
file contradicting it makes dira lie about a decision, and that is the one failure
the product cannot survive.

## Constraints that bind this lane

- **Deletable at any moment, correct anyway.** Every query answers correctly with no
  cache present. The cache is an accelerator; the same code path must produce the same
  answer without it.
- **Staleness detection cannot be skipped for speed.** If validating the cache costs
  more than reading the files, the cache is pointless — say so rather than shipping a
  check the fast path bypasses.
- **A SQLite dependency is a cost against `int-0002` and `dec-0001`.** Pure-Go
  (`modernc.org/sqlite`) versus cgo (`mattn/go-sqlite3`) changes cross-compilation,
  binary size, and cold start, and E0's goreleaser matrix has to build it for
  darwin-arm64 and linux-amd64. If your reading of the evidence is that no SQLite at
  all beats SQLite at 200 entries, **say that in your output** — but do not
  unilaterally drop it: `dec-0002` and L0 both name it, so removing it needs a
  superseding entry, not a silent omission.
- **No daemon, no background warmer, no watcher process** (`int-0002`).
- The cache holds **no** execution status and no derived kazi state (`dec-0004`).
  That join is E4's and is computed at read time.

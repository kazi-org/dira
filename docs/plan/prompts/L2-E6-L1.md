**Why this lane exists.** `DESIGN.md` inherits two tests to E6 — a contrast matrix
reporting 0 failures with hover exceeding rest in both schemes, and a 3-viewport × 2-scheme
render gate. The render gate exists as `docs/design/scripts/render.mjs` and works. **The
contrast matrix does not exist as an artifact**; it was run ad hoc during the design phase
and cannot currently be re-run, which makes an inherited requirement unenforceable. And
`docs/plan.md` §E6 requires pixel fidelity "within the pixel tolerance recorded in
DESIGN.md" — **no tolerance is recorded anywhere.** This lane closes both gaps and builds
the fixture ledger that makes a pixel comparison meaningful.

### E6-L1-T1 — Install the `web-interface-guidelines` skill

Vercel's `web-interface-guidelines` is the authority for E6's implementation layer and is
**not currently installed**. Skills are global-only — `~/.claude/skills/`, never
project-local.

**acc:** `~/.claude/skills/web-interface-guidelines/SKILL.md` exists and is the real
guideline set, not a placeholder — `grep -cE '^[0-9]+\.' ` over the skill's content
returns ≥10 numbered guidelines, and the skill appears in the harness's available-skills
listing.

### E6-L1-T2 — Write the contrast matrix as a re-runnable script with a negative control

`DESIGN.md` requires 0 failures across all 42 fg/bg pairs in both schemes, with
`--bearing-lift` exceeding `--bearing` in contrast on every surface/scheme combination
(WEB.md 2). Parse the token values out of `tokens.css` rather than duplicating them —
a second copy of the palette is the defect this script exists to catch.

**acc:** `node docs/design/scripts/contrast.mjs` exits 0 and prints `0 failures` plus an
explicit `hover > rest` result for each of the six surface × scheme combinations
(`--ground`, `--panel`, `--sunk` × light, dark), reporting the computed WCAG ratio per
pair; `node docs/design/scripts/contrast.mjs --probe-regression` substitutes the pre-r4
light `--bearing-lift` value `#b8862f` and exits non-zero reporting ≥1 failure **and** at
least one `hover < rest` inversion; and the script reads its palette from `tokens.css`
such that editing a hex in `tokens.css` changes the reported ratios.

### E6-L1-T3 — Write the pixel-diff script with a two-sided self-test

Compares two PNGs and reports the percentage of pixels differing by more than a
per-channel threshold. It will be run against 2× device-scale-factor captures.

**acc:** `node docs/design/scripts/pixeldiff.mjs <a> <a>` reports `0.00%` and exits 0;
the same script on any light capture against its dark pair reports `>1%` and exits
non-zero; a `--tolerance` flag is honoured such that a diff above it exits non-zero and
below it exits 0; and running it against images of differing dimensions fails loudly
rather than silently cropping.

### E6-L1-T4 — Extend `render.mjs` to fail on any non-loopback asset request

`cst-0004` and `dec-0010` both hinge on the rendered surfaces fetching nothing from
anywhere. The existing gate catches *failed* requests but would happily pass a page that
successfully loads a webfont from a CDN. Add a gate check that records every request URL
and fails any whose host is not `127.0.0.1`.

**acc:** `render.mjs` gains a gate check that fails a target loading any asset from a
non-loopback host — demonstrated by a throwaway fixture page referencing an external
stylesheet, which the gate rejects naming the offending URL — while
`node docs/design/scripts/render.mjs <iter>` over the three committed screens still
reports `GATE PASS`; and the existing checks (console errors, failed requests, blank
mount, byte-identical light/dark pair, layout shift) still fire, proven by leaving them
unmodified in the diff.

### E6-L1-T5 — Build the design fixture ledger that reproduces the mockup content

The mockups contain content that is not in the real ledger: `dec-0011`, `qst-0006`, the
orphan `int-0004` behind the drift row, and `kazi:prop-8a1f`. A pixel comparison between a
Go-served page and a mockup is only meaningful if both render **the same content**, so the
fixture ledger must reproduce the mockups' text exactly, one file per entry (`dec-0002`).
This is a fixture, not a change to `.dira/` — the real ledger stays untouched.

**acc:** every file under `docs/design/fixtures/ledger-design/entries/` validates against
`schema/entry.schema.json`; the fixture's entry titles, `because` bodies, alternative
names, `why_not` text, and `revisit_if` text are byte-equal to the corresponding strings
in `docs/design/screens/s1-decision.html`, `s2-index.html`, and `s3-distill.html`, proven
by a script that extracts both and diffs them; the fixture contains the orphan intent that
produces the drift row and the staged entries that populate `/distill`; and
`.dira/entries/` is unchanged by this task.

### E6-L1-T6 — Reconcile `DESIGN.md` with `tokens.css` and record the pixel tolerance

Two documentation defects. First, `DESIGN.md`'s *Hues* table disagrees with `tokens.css`
in three of four rows — `--bearing` light (`#9a6c1c` vs `#8a5f18`), `--bearing-lift` light
(`#b8862f` vs `#6d4a12`), `--caught` dark (`#d4614d` vs `#d97060`). `tokens.css` is the
declared single source, so the table is stale and must follow it. Second, no pixel
tolerance is recorded, which makes the L0 `acc:` clause that cites one unfalsifiable.
Set the tolerance from measurement — capture the same screen twice and see what the
environment's own noise floor is — not from a guess.

**acc:** every hex in `DESIGN.md`'s hue table appears in `tokens.css` at the same token and
scheme, checked by a script that extracts both and diffs them (and which fails if a value
is edited in either file alone); `DESIGN.md` states a numeric pixel tolerance with the
measurement that justifies it, the threshold definition it uses, and the command that
checks it; and `DESIGN.md` documents `contrast.mjs` and `pixeldiff.mjs` alongside
`render.mjs` in the *Verification* section, including the negative-control invocations.

**This lane is the growth engine, and its central claim is falsifiable.** `dec-0010` promotes
the renderer ahead of the paid apps because dira is invisible by design: nothing to
screenshot, nothing to link, no page for a stranger to land on. The same entry states the
constraint the renderer lives under — it "stores nothing, owns no user data, requires no
account to view, and the CLI behaves identically whether it exists or not. If it disappeared
tomorrow, no user loses a capability. An audience that checks this claim will check it, so the
honesty has to be structural rather than reassuring." **The tests in this lane are that
structure.** They are not a formality; they are the only reason the claim can be made in copy.

## A decision this lane must record before it builds

`dec-0010` settles *that* the renderer ships and that it stores nothing. It does **not**
settle what serves it, and that gap has to be closed explicitly rather than by whichever
mechanism gets coded first. `docs/design.md` §9 puts hosted rendering in Tier 3, "much
later". `dec-0005` already rejected dira-operated infrastructure for sync on ops-burden
grounds — a solo maintainer cannot carry on-call and a security surface alongside kazi — and
that reasoning transfers to a rendering service unchanged.

**The proposal this lane plans against:** `dira render` emits static HTML that the user
deploys to their own GitHub Pages (or any static host, or opens from `file://`). M6 then needs
no dira-operated infrastructure at all, the export is trivially auditable for the "stores
nothing" claim, and `cst-0004` holds by construction rather than by policy. The
`.dira/entries/` markdown remains the permanent no-JavaScript floor `dec-0010` names.

If you believe a stateless read-through service is the right mechanism instead, say so in your
output with reasoning — **do not plan both**, and do not silently pick one. T1 exists to
record whichever is chosen, with its rejected alternatives.

### E6-L5-T1 — Record the delivery-mechanism decision as a ledger entry

See *A decision this lane must record* above. Write it as a decision entry with the rejected
alternatives and their `why_not`: a dira-operated stateless read-through service (ops burden,
on-call, and a security surface a solo maintainer cannot carry alongside kazi — `dec-0005`'s
own reasoning), a hosted service that stores ledgers (already rejected by `dec-0010` as a
`cst-0004` violation), and GitHub's own markdown rendering (the permanent floor, not the
primary surface). Update `docs/design.md` §9 so Tier 3 and this mechanism do not read as the
same thing.

**acc:** a new entry exists at `.dira/entries/dec-00NN.md` taking the next free `dec-` id,
with `kind: decision`, `state: accepted`, a `derives_from` edge to `dec-0010`, an `informs`
edge to `cst-0004`, and ≥3 populated `alternatives` each carrying a `why_not`; it validates
against `schema/entry.schema.json`; it introduces no dangling edge (every `to:` resolves to an
existing entry id or a namespaced external ref); and `docs/design.md` §9 distinguishes this
mechanism from Tier 3 hosted rendering and cites the new entry.

### E6-L5-T2 — Implement `dira render` reusing the served templates

One code path, two outputs: `dira ui` serves it, `dira render` writes it. A forked template
set would drift and the fidelity gate would only cover one of them. Output is a directory of
static HTML plus `tokens.css`, all links relative so it works from `file://`, from a
subdirectory of a GitHub Pages site, and from a domain root.

**acc:** `dira render --out <dir>` over the repo's own `.dira/` writes one page per entry plus
an index, such that every id under `.dira/entries/` is reachable from the index by following
links only (verified by a link-walk that also reports zero broken internal links); every page
opens correctly from `file://` with zero requests to any host, verified by a capture that
records network activity; a Go test asserts `internal/render` and `internal/ui` share the same
`template.Template` set (adding a template to one makes it available to the other, and
duplicating one fails the test); the output is deterministic — two runs on the same ledger
produce byte-identical files; and `dira render` writes nothing outside `--out`.

### E6-L5-T3 — Strip every mutating affordance from the export

A public render is read-only in the strongest sense: there is nothing on the page that could
change anything, and no page that offers to. `/distill` does not exist in an export.

**acc:** the export contains zero `<form>`, `<input>`, `<textarea>`, `<button>` elements and
no `method="post"` anywhere, asserted by a grep over every emitted file; no page corresponding
to `/distill` is emitted and no link to one exists; every `<a href>` in the export resolves
either to another exported page or to an absolute external URL that is not dira-operated; a
test **fails** if a template gains a `<button>` reachable from the export, demonstrated; and
the export sets no cookie and includes no analytics, beacon, or telemetry code, asserted by
grep for `fetch(`, `XMLHttpRequest`, `navigator.sendBeacon`, and `<script src`.

### E6-L5-T4 — Write the privacy-leak suite

`cst-0003` rule 3 names a hosted render explicitly and says a violation is a security bug.
The suite has to test the boundary from the outside: build a fixture with a private parent
ledger and a public child, export the child, and assert nothing from the parent is present
except refs.

**acc:** against a fixture pair (a `tier = "person"` ledger and a public repo ledger whose
entries carry `derives_from` refs into it, plus at least one entry marked `private: true` in
the public ledger), the export of the public ledger contains none of the private entries'
titles or body text in any position — page text, `<title>`, `alt`, `aria-label`, `<meta>`,
HTML comments, or file names — while the refs themselves are present; the suite **fails** when
the resolver is made to inline a private parent's title, demonstrated; entries marked
`private: true` in the public ledger are absent from the export entirely, including from the
index and from any roll-up count; and the suite asserts the same for `dira ui`'s served output,
because `cst-0003` does not distinguish the two.

### E6-L5-T5 — Write the network-unplugged suite across every core verb

`cst-0004` names the verbs: "capture, `brief`, `why`, `map`, `check`, `ui`". `dec-0010` adds
the claim that the CLI behaves *identically* whether the renderer exists or not. Both are
testable, and "identically" means byte-comparable output, not "still works".

**acc:** a suite runs `dira log`, `why`, `brief`, `map`, `check`, `ui` and `render` against a
fixture ledger with all non-loopback network access forced to fail — every outbound dial to a
non-loopback address errors — and all seven exit 0; each verb's stdout is byte-identical to the
same invocation with network access available, for every verb whose output is deterministic
(and any exception is named explicitly with its reason); the suite **fails** if any code path
attempts a non-loopback dial, reporting the address, demonstrated by temporarily adding one;
no verb reads or writes any credential, config, or cache outside the repo and the documented
config path, asserted by the test; and the suite is part of `go test ./...` rather than a
manual procedure.

### E6-L5-T6 — Make the export crawlable and landable for a signed-out stranger

Channel 4 in `.agents/product-marketing.md` §7 is long-tail SEO: "every rendered decision page
is a page answering *why did project X choose Y*". That only compounds if the pages are
crawlable and each one stands alone for someone with no context. The `.legend-key` (which
closes the jargon gate) and the single `.take` conversion block are the recorded answers to
that, and both must survive into the export. Copy follows §10's voice rules: no virality
claim, and nothing implying the renderer is required.

**acc:** every exported page carries a unique `<title>` and `<meta name="description">` derived
from its entry, an `og:title`/`og:description` pair, and a canonical URL that is correct when
the export is deployed under a subdirectory; the export includes a `sitemap.xml` listing every
page and a `robots.txt` that permits crawling; the attribution sentence appears exactly once
on every page as a sentence with no badge or image, byte-equal to the string recorded in
`DESIGN.md`; the index carries the `.legend-key` and exactly one `.take` block, both visible
with JavaScript disabled and neither hover-revealed; a grep over all exported copy finds none
of "revolutionary", "seamless", "supercharge", "10x", "AI-powered", or any claim that the
renderer is required; and the export passes `render.mjs`'s full gate plus `contrast.mjs` at
`0 failures` with `hover > rest`.

### E6-L5-T7 — Document the deploy path and the additivity claim

A renderer nobody can deploy in five minutes does not close the loop. Document the path from
`dira render` to a live public URL on the user's own infrastructure, and state the additivity
claim in the same place — `dec-0010` and `.agents/product-marketing.md` §7 both require the
distinction to be stated explicitly wherever the renderer is mentioned, "or it will read as a
broken promise to exactly the audience that checks". Docs land with the code.

**acc:** `README.md` documents `dira render` with a copy-pasteable path to a live public URL on
the user's own hosting, and states in that section that the renderer is read-only, stores
nothing, requires no account to view, and that the CLI behaves identically without it; every
command in that documentation runs successfully from a clean checkout, verified by executing
them in order; `DESIGN.md`'s *Verification* section lists the leak suite and the
network-unplugged suite with their invocations; and no documentation added by this lane claims
virality or implies the renderer is required.

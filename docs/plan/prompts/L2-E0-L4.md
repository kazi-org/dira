## Established facts and decisions this lane inherits

- **The tag-push path must work with no secrets.** `GITHUB_TOKEN` can create a
  Release in its own repo, so the lane `acc:` is verifiable today. kazi gates its
  release-please job behind `vars.RELEASE_AUTOMATION == 'true'` because
  release-please additionally needs the org setting "Allow GitHub Actions to create
  and approve pull requests" and, for hands-off merges, a PAT. Mirror that gate — but
  keep `on: push: tags: v*` unconditional, so nothing in this lane's verification
  waits on a human provisioning anything.
- **`CGO_ENABLED=0` for every target.** It is what makes darwin binaries
  cross-buildable from a Linux runner and keeps the single-static-binary promise of
  `int-0002`.

  **Consequence, stated deliberately so E1 does not discover it:** this forecloses
  `mattn/go-sqlite3` for E1's derived cache and points E1 at a pure-Go SQLite
  (`modernc.org/sqlite`). Note in your output that this deserves a `.dira/` decision
  entry — **do not write one**; capture belongs to E2's flow and the decision is the
  maintainer's, not this lane's.

- **Do not mimic kazi's raw-binary asset naming.** kazi publishes bare
  `kazi_macos_aarch64` files because Burrito emits them. goreleaser's default is a
  `.tar.gz` archive plus `checksums.txt`, and its Homebrew generator, `brew`, and
  every goreleaser-shaped consumer expect archives. Take the goreleaser defaults and
  **state the divergence in a comment**, so a later session does not "align the two
  pipelines" by hand and break E0-L5's formula.
- **Targets:** darwin-arm64 and linux-amd64 are the `acc:` floor. darwin-amd64 and
  linux-arm64 are nearly free with `CGO_ENABLED=0` and kazi ships all four. Adding
  them is fine; a target you add is a target E0-L5's formula must have a checksum
  for, so decide once and keep the two lanes' target lists identical.

## Constraints that bind this lane

- **Pin every action to a 40-char commit SHA**, matching E0-L3 and kazi.
- **`permissions: contents: write`** on the release job only — that is the minimum
  for creating a Release and uploading assets. Nothing else in the workflow needs it.
- **Smoke-test before publishing, not after.** kazi executes `--help` on the built
  binary and fails the job before the upload step, so a broken or wrong-arch binary
  never reaches a Release. Do the same with `dira --version`: it also proves the
  ldflags wiring, which is the part most likely to be silently wrong. A native-arch
  runner is required to execute a native binary — plan which runner executes which
  target.
- **The version in the binary must equal the tag.** `-ldflags -X` against the path
  E0-L1 established, with the leading `v` stripped. This is the one clause of the
  `acc:` line a stub cannot fake.
- **No hand-written release notes step that blocks the build.** Notes are exhaust;
  binaries are the deliverable.
- **`README.md`** gains a truthful download/install-from-release section once this
  lane's `acc:` is green. `brew install` prose belongs to E0-L5.

## The task bound

**≤8 tasks.** Each task carries exactly: `id` (`E0-L4-T<n>`), `title`, `files` (real
paths — `.goreleaser.yaml`, `.github/workflows/release.yml`,
`release-please-config.json`, `.release-please-manifest.json`), `acc:` (one
machine-checkable predicate at task granularity), `depends_on`.

Predicates must assert an observed artifact or run. `acc: .goreleaser.yaml exists` is
vacuous; `acc: goreleaser check passes and goreleaser build --snapshot --clean emits
dist/ artifacts for darwin/arm64 and linux/amd64` is not. Split the locally-verifiable
half (`goreleaser check`, snapshot build) from the CI-verifiable half (the real tag
push) so a failure localises.

**Name the test tag explicitly and say it is disposable.** A `v0.0.1-rc.1` tag and its
Release are cleanup, not history — the task that creates it owns deleting it.

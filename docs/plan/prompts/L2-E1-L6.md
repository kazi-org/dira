else. **Write no Go code.**

## Context

**Epic:** E1 — the ledger (`docs/plan/lanes/E1.md`), roadmap M1.
**Lane:** `E1-L6`. **depends_on:** `E1-L3` (the cache and `dira reindex`), `E1-L5`

**Lane `acc:` verbatim:**

> a committed test executes the built `dira` binary as a subprocess against the
> 200-entry fixture with `.dira/cache/` removed before each run, and fails if the
> median of N≥20 cold runs exceeds 100ms wall clock or if any single cold run exceeds
> 150ms; the same test fails if warm `dira brief` exceeds the cold budget, and if
> `dira reindex` over 200 entries exceeds a budget stated in the test; the run happens
> with no network available and the test asserts the binary opened no socket; and the
> budget numbers live in one place in the test so a regression names which budget it
> broke.

**What this lane is for.** `int-0002` states the achievement condition literally:
*"`dira brief` returns in well under 100ms on a cold cache."* dira runs in the latency
path of a human waiting for a prompt to return, several times per session. The epic
prompt was explicit that this is **measured against a 200-entry fixture, not
assumed** — which is why it is a lane rather than a footnote.

**You own a number you do not own the code for.** Meeting it may require changing
decisions inside `E1-L1`, `E1-L3`, and `E1-L5` — lazy body parsing, not reading 200
markdown bodies to render eight titles, skipping a cache open on the happy path. Your
owner is **explicitly authorized to modify those packages**; otherwise this lane can
only file bugs, which is not a lane.

## Constraints that bind this lane

- **Measure the shipped binary, as a subprocess.** Not an in-process benchmark, not
  `go run`. Process start, config load, cache miss, files read, render, exit — the
  whole thing the hook pays for.
- **Cold means cold.** `.dira/cache/` removed before each run. Warm-cache numbers are
  a separate, additionally-asserted budget.
- **The gate must fail in CI, on CI hardware.** A benchmark that is only green on the
  maintainer's laptop is worth nothing. CI runners are slower and noisy, so decide
  in-lane between a stated CI multiplier, a higher-percentile threshold with a
  documented N, or a dedicated runner — and state the reasoning in the task. A flaky
  gate that gets disabled after three false alarms is worse than a slower stated
  budget that holds.
- **No daemon, no resident process, no warm-up trick** (`int-0002`). Meeting the
  budget by keeping something alive violates the constraint the budget exists to
  protect.
- **The no-socket assertion has to be real.** Decide how it is checked (a test running
  with no route, an environment with DNS unavailable, or a syscall-level check) and
  state the limits of the method rather than asserting more than the check proves.
- **Do not raise the budget to make the test pass.** 100ms is `int-0002`'s stated
  achievement condition; raising it needs a superseding entry with a reason, not a
  constant edit. If you conclude the number is unreachable with the current design,
  say so in your output with what it costs to reach it.

## Task bound and required fields

Produce **at most 8 tasks.** This lane should be *small* — likely 3 to 5 tasks. Each
needs `id` (`E1-L6-T<n>`), `title`, `files`, `acc:` (a command and an observable
outcome; red before, green after), and `depends_on`.

Provisional paths (reconcile against E0): a performance test package (e.g.
`internal/perf/` or `test/perf/`), plus the CI workflow file E0 created.

**Your task set must cover all of the following:**

1. The measurement harness: build the binary, run it N times cold against the
   fixture, report median and max, one place for the budget constants.
2. The CI gate, with the runner-variance policy decided and stated.
3. The warm-cache and `dira reindex` budgets.
4. The no-network assertion, with its method's limits stated.
5. **A contingency task for the optimization work**, scoped by what the harness
   actually measures — not a speculative list of optimizations. If the first
   measurement is already green, that task's `acc:` should be the profile evidence
   showing where the remaining headroom is, so the next regression is diagnosable.

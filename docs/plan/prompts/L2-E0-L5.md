## The prerequisite only a human can satisfy

The auto-bump needs a **`HOMEBREW_TAP_TOKEN`** secret on `kazi-org/dira`: a
fine-grained PAT with `contents:write` on `kazi-org/homebrew-tap` **only**. kazi
already uses a secret of that name in its own repo; secrets are per-repo, so dira
needs its own. Minting it requires the repo owner.

**Plan the whole lane anyway.** Follow kazi's failure-tolerant convention: the publish
step warns and skips when the token is absent, so the binary release stays green while
the brew half waits. Structure the tasks so that everything except the final live
verification is landable and verifiable today, and name the one predicate that cannot
go green until the secret exists. Report that dependency in your output — do not
silently plan around it, and do not block the lane on it.

## The risk this lane must actively guard

**Two release pipelines now write to one tap repo.** kazi's `tap-bump` does
`git add Formula/kazi.rb` — a single named path — for exactly this reason. If dira's
publisher does `git add -A`, force-pushes, or uses a generator that rewrites the
`Formula/` directory, it clobbers `Formula/kazi.rb` and breaks `brew install kazi` for
every kazi user. That is a production failure **in another product, caused by this
lane.**

So: stage only `Formula/dira.rb` by name, never force-push, and make
"`Formula/kazi.rb` is byte-unchanged" an asserted predicate rather than an intention.
A task whose `acc:` is a `git diff` over `Formula/kazi.rb` across the release's commit
range is cheap and is the difference between a guard and a hope.

Consider also: goreleaser can generate and push the formula itself, which is less
shell than kazi's heredoc but hands directory-level write behaviour to a tool you did
not audit against a shared tap. Whichever you choose, the byte-unchanged predicate is
non-negotiable — decide it deliberately and record the reason.

## Constraints that bind this lane

- **A formula, not a cask.** Homebrew casks are macOS-only, and E0's L0 `acc:`
  requires a linux-amd64 binary. The existing `Formula/kazi.rb` already serves Linux
  via `on_linux`; match that shape so one tap behaves consistently.
- **Match E0-L4's asset naming.** E0-L4 takes goreleaser's default `.tar.gz` archives
  rather than kazi's bare-binary naming. `Formula/dira.rb` therefore installs from an
  extracted archive, and will **not** look like `Formula/kazi.rb`'s
  `Dir["kazi_*"].first`. That asymmetry inside one tap is deliberate — comment it in
  the formula, or a later session will "fix" it.
- **The formula is generated, never hand-edited.** `Formula/kazi.rb` carries a
  `# Generated by ... Do not hand-edit.` header. Do the same. The last clause of the
  `acc:` line — a second release bumps it with no human edit — is what proves it.
- **The `test do` block must assert something real.** kazi's asserts `--help` output
  contains `kazi`, which a stub satisfies. Assert the **version**: the installed
  binary's `--version` matching the formula's `version` catches a formula pointing at
  a stale release, which is the actual failure mode of a generated formula.
- **License:** Apache-2.0, per `LICENSE` and `NOTICE`. Confirm rather than copy
  kazi's line on trust.
- **`README.md`** gains the `brew install kazi-org/tap/dira` instruction only once
  the install predicate is observed green. A README documenting an install command
  that does not work is worse than one that omits it.

## On `qst-0004` (open — and not a blocker)

`qst-0004` asks whether the name "dira" is clear of collisions on the channels that
matter. A `dira` in homebrew-core would not affect

short form. Note the discrepancy in your output; resolving it belongs to `qst-0004`.

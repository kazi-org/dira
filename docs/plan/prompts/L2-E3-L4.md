# L2-E3-L4 — `dira supersede`, proven by a red-to-green enforcement flip

You are an L2 planner. You produce **tasks**, not code, and not lanes.

## Context

**Epic:** E3 — the enforcer. Supersession must **actually change enforcement**: the
superseded entry stops being enforced, its superseder starts. A version that only
relabels state is the failure to design against, because the enforcer would keep citing
a decision the user has already overruled — and one week of that gets `dira check`
switched off.

**Your lane:** E3-L4. The `dira supersede` verb, plus the check's behaviour when an input
matches an entry that is *already* superseded: report and redirect to the superseder,
never `✗`. The lane's proof is a single red-to-green pair across one command.

`dec-0001` states the design intent directly — *"overruling this is a one-line
supersede — the alternative is recorded above with its own revisit condition, which is
the point of writing it this way."* dira's own ledger is the acceptance test for whether
that sentence is true.

**depends_on:** E3-L1 (fixtures), E3-L2 (the verb, the enforcement set, the renderer).
**Cross-epic prerequisite:** E1's entry **writer** — this is the only write verb in E3.

**Your lane's `acc:` line, verbatim:**

> in one test against `internal/enforcer/testdata/ledgers/supersede`,
> `dira check "add a background daemon"` exits 2 citing dec-0060; after
> `dira supersede dec-0060 --with dec-0061`, the identical command exits 0, no output
> cites dec-0060, and a conflict fabricated against dec-0061's own alternatives is now
> cited instead; dec-0060's file reads `state: superseded` with `updated` bumped,
> dec-0061 carries a `supersedes` edge to dec-0060, both still validate against
> `schema/entry.schema.json`, and no other entry file changed (tree digest);
> `dira check` on an input matching the now-superseded dec-0060 emits an informational
> line naming dec-0061 and **no** `✗`; and `dira supersede me:cst-0002 --with cst-0005`
> exits non-zero, writes nothing, and leaves the parent ledger byte-identical.

## Fixed before you start

- The enforcement set from `docs/plan/lanes/E3.md`: `superseded` decisions and
  `superseded` constraints are **not** enforced, and a match against one is reported
  with a redirect rather than raised as a conflict.
- Exit codes `0`/`1`/`2` and the message format come from E3-L2. A refusal (an invalid
  supersede target) is `1` — dira's own error — not `2`.
- **No upward write, ever.** `cst-0003` rule 1: a child reads its parents and dira has no
  verb that writes to a parent. `dira supersede` on a namespaced ref pointing into a
  parent ledger must refuse and write nothing.
- `mirror.adr` is `true` in this repo's config. Per `dec-0009`, the ADR is exhaust: a
  supersede regenerates the mirrored ADR and never reads one back, and deleting every
  ADR must lose no information.

## The risk to plan against

`dec-0002` bought one-file-per-entry precisely so that **one write is a complete
mutation** — no two-file transactions, therefore no partial commits. `dira supersede`
breaks that property: it edits two entry files (the target's `state`, the superseder's
`supersedes` edge). It is the one place in E3 where a crash mid-command can leave the
ledger in a state no verb produced.

Decide and test the failure mode explicitly. Two defensible shapes: write the
superseder's edge first so a crash leaves a claimed-but-unflipped pair that a later
`dira reindex` or a `dira check` warning can detect; or stage both writes and roll back
on any error. Either is acceptable; leaving it undecided is not, and discovering it after
a crash is worse. At least one task should own the interrupted-write behaviour with its
own predicate — e.g. injecting a failure between the two writes and asserting the ledger
is still readable and the inconsistency is reported rather than silent.

## The task bound

**≤8 tasks.** Each task needs: `id` (`E3-L4-T<n>`), `title` (one line, imperative),
`files` (actual paths), `acc:` (one machine-checkable predicate — a command and an
observable outcome), `depends_on` (task ids or `none`).

An `acc:` line that is green before the task runs is a defect. `acc: dira supersede
exists` is exactly the vacuous predicate kazi is built to catch.

Seams where the work divides — **guidance, not your task list:** the `supersede` fixture
ledger (dec-0060 plus a dec-0061 that permits a daemon under its own new terms); the
verb's argument parsing and validation; the two-file mutation and its interrupted-write
behaviour; the refusal path for cross-ledger targets; the check's superseded-match
redirect; the ADR regeneration path; the end-to-end red-to-green test.

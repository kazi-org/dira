# L2-E4-L2 — Ledger-side buckets and decision-blocked detection

You are an L2 planner. Decompose **one lane** into tasks and write them to
`docs/plan/tasks/E4-L2.md`. Planning only — write no Go code.

## Context

**Epic:** E4 — Derived status (`docs/plan.md` §E4, roadmap M4).

**Lane:** `E4-L2` — Derive the ledger-side buckets and decision-blocked detection, with
**no kazi involved**. This lane never shells out and never reads kazi's JSON. It answers
the two questions dira can answer alone: *what was decided and never planned*, and *what
is stalled because a human never answered a question*.

**Decision-blocked is the differentiator.** `dec-0004` and `docs/design.md` §6.1 both
say so: an open question with a `blocks` edge gates work **before any goal exists**, so
it appears in no execution tracker anywhere. It is also the load-bearing row for the
whole product's claim. Treat it as the point of this lane, not a case it handles.

**`acc:` (verbatim):**

> `go test ./internal/status -run 'TestLedger|TestDecisionBlocked'` passes over
> `testdata/ledgers/` where: an accepted decision with no `realized_by` edge lands in
> `ToBePlanned` and an active intent with none does too; an **open** question carrying
> `blocks → dec-X` puts `dec-X` in `DecisionBlocked` naming the question's id and title,
> found **without `dec-X` itself carrying any edge** (edges live on the subject, so this
> requires the inbound-edge index, not a scan of `dec-X`); flipping that question to
> `state: answered` moves `dec-X` back to `ToBePlanned` with no other diff; a question
> blocking an entry whose own state is `superseded` produces no `DecisionBlocked` row;
> `achieved` and `abandoned` intents are reported as their own terminal ledger-side
> groups and never as `ToBePlanned`; and `go list -deps ./internal/status` shows
> `os/exec` is **not** reachable from this package, with the tests additionally passing
> under an emptied `PATH`.

**depends_on:** `E0` (buildable module), `E1` (the entry reader and the derived cache's
**inbound-edge index**). No E4 lane.

## Read first

1. `docs/plan.md` §E4 and §E1 — your L0 clause, and what E1 owes you.
2. `docs/plan/lanes/E4.md` — the lane table, your lane's risk, and the boundaries
   section. Note **the inbound-edge index is E1's**, not yours.
3. `.dira/entries/dec-0004.md` — the six-bucket join table. Rows 1 (*To be planned*) and
   6 (*Decision-blocked*) are yours; the other four need kazi and belong to E4-L3.
4. `schema/entry.schema.json` — read the `$defs/edge` block carefully. Two facts decide
   your design: `blocks` is described as *"this entry gates another; the source is
   typically an open question"*, and the schema's own note says **"Edges are stored on
   the SUBJECT entry"**. So the edge that makes `dec-X` decision-blocked lives on the
   *question's* file, not on `dec-X`. Also read the `state` enum and the per-kind
   `allOf` constraints — `open`/`answered` belong to questions, `achieved`/`abandoned`
   to intents.
5. `.dira/entries/cst-0002.md` — five kinds, closed. There is no "blocked" kind and you
   must not invent one; blocked is a *derived view*, not an entry.
6. `.dira/entries/dec-0002.md` — one file per entry, so any index you use is derived and
   disposable.
7. `docs/design.md` §6.1 and §6.4, and `docs/design/screens/s2-index.html` — the
   vocabulary the CLI will use (`to be planned`, `blocks this`). E4-L4 owns rendering;
   you own the derivation and its names.
8. `.dira/entries/` itself — the real 23-entry ledger, which already contains a live
   example: `qst-0003` has a `blocks` edge, and `qst-0005` blocks `dec-0008`. Use the
   real ledger as one of your fixtures rather than only synthetic ones.

No dira Go source exists yet. This lane creates `internal/status/` — you own `types.go`
(the bucket enum and the per-entry result type), `ledger.go` and `blocked.go`. **E4-L3
adds `join.go` to the same package and consumes your exported types.** Define those
types precisely in your task file so E4-L3 needs no conversation with you.

## Tasks — at most 8

Each task needs `id` (`E4-L2-T<n>`), `title`, `files`, `acc:`, `depends_on`.

Suggested spine — refine it, but do not lose a clause of the lane `acc:`:

1. **Confirm E1's inbound-edge index exists and is queryable**, or state plainly that it
   does not. `acc:` names the E1 API you call. If it is missing, your output says so
   rather than building a private index (see the honesty rule — this is the most likely
   thing to block this lane).
2. **The shared types** — the six-bucket enum, the per-entry row, the `Source` field
   E4-L3 will set. `acc:` should include a compile-time assertion that the enum has
   exactly six values and that no value spells an entry `state`.
3. **The ledger fixtures**, including the real `.dira/` and the four negative cases in
   the lane `acc:` (answered question, superseded target, achieved intent, abandoned
   intent).
4. **`ToBePlanned` derivation** — accepted decisions and active intents with no
   `realized_by`, with a test that an entry *with* a `realized_by` edge is excluded even
   when kazi is unreachable (it is not to-be-planned, it is *unknown*; that distinction
   is E4-L3's, so your output must leave room for it rather than absorbing it).
5. **`DecisionBlocked` derivation** — the reverse lookup, the open/answered flip, the
   superseded-target exclusion, and naming the blocking question's id **and** title.
6. **Terminal ledger groups** — achieved and abandoned intents as their own groups.
7. **The no-subprocess structural test** — `go list -deps` plus the emptied-`PATH` run.

## Established facts — do not spend a task rediscovering these

The real ledger has been checked against the schema and against the four invariants
below. **Current state: 22 entries, zero problems.** So:

- Every positive-path predicate you write is red today only because no Go test
  exists — not because an entry is broken. If a task's `acc:` goes red on a *real*
  entry, you have found either a genuine new drift or a bug in the validator; treat
  it as the latter first.
- `format: date-time` is an **annotation, not an assertion**, in JSON Schema
  2020-12. Most Go libraries do not check it unless format assertions are explicitly
  enabled. `created`/`updated` therefore pass a naive validator no matter what they
  contain. Decide explicitly whether to enable format assertions or to check RFC3339
  yourself, and make it a task.

## The four invariants JSON Schema cannot express

This is the crux of the lane. A validator that only shells out to a schema library
satisfies half the `acc:` line and leaves the ledger able to rot exactly where it
actually rots:

1. **`edge.to` has no pattern.** `$defs/ref` defines the ref grammar and is
   **referenced by nothing** — `edge.to` is a bare `string`. So `to: "banana"` is
   schema-valid.
2. **Dangling edge targets.** A `derives_from`/`informs`/`blocks`/`supersedes` edge
   pointing at a nonexistent local id is schema-valid. Two exceptions that must
   **not** be flagged: `realized_by`, whose target is an external URI
   (`kazi:goal-x`), and any namespaced ref (`sire:int-0002`, `me:cst-0002`), which
   resolves through another ledger — E5 owns that resolution and is blocked, so at E0
   a namespaced ref is accepted without resolution.
3. **`id` prefix vs `kind`.** `id: dec-0001` with `kind: intent` passes the schema.
   The prefix→kind map is `int`→intent, `dec`→decision, `qst`→question,
   `cst`→constraint, `note`→note.
4. **`id` vs filename.** `dec-0002.md` containing `id: dec-0003` passes the schema,
   and breaks every `dira why` lookup that resolves an id to a path.

Report in your output whether you think the schema itself should gain
`"$ref": "#/$defs/ref"` on `edge.to`. **Do not plan that change** — editing
`entry.schema.json` alters a published contract (`$id` is a public URL) and is a
decision for the ledger, not for this lane.

## Constraints that bind this lane

- **Embedding.** `go:embed` cannot reach above its own package directory. The clean
  answer is a `package schema` file **inside** `schema/`, embedding
  `entry.schema.json` as a sibling. Do not move or copy the schema file: its `$id`
  is `https://github.com/kazi-org/dira/schema/entry.schema.json` and duplicating it
  guarantees the two copies diverge. The validator must read the **embedded** copy,
  not a path on disk, or the shipped binary validates nothing.
- **Dependencies.** A draft-2020-12 validator and a YAML→JSON step are legitimately
  third-party (`dec-0001` explicitly says the stdlib covers dira's needs "SQLite via
  a single dependency" — it does not claim a JSON Schema implementation). Keep them
  out of `./cmd/dira`'s build graph at E0 so E0-L1's dependency predicate stays
  green. Prefer converting YAML frontmatter to JSON before validating, so the value
  types the validator sees are exactly the types the schema describes — a YAML
  decoder that yields non-string map keys or untyped ints will produce false
  failures.
- **Two-sided by construction.** A test that only asserts the real ledger is valid
  is green on an empty validator. The negative-fixture half is what makes it a gate.
  A fixture that unexpectedly passes must fail the suite loudly — not be skipped, not
  be logged.
- **Failure messages are the deliverable.** `validation failed` is useless in CI.
  Each failure names the file, the field path, and the rule.

## Fixture guidance

Negative fixtures live in `internal/ledger/testdata/invalid/` (adjust the package
path to E0-L1's layout). Beyond the eight the `acc:` line requires, these are cheap
and catch real classes: an `alternative` missing `why_not`, an unknown `edge.type`,
a `title` over 120 characters, an uppercase tag, duplicate tags, a `source.tier`
outside the enum.

Include at least one **positive** fixture exercising what the real ledger does not
yet contain: a namespaced ref, a `realized_by` edge with a `kazi:` URI, an `updated`
field, and `private: true`. Otherwise the first entry to use those features is the
test case.

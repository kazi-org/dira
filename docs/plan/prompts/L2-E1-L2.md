**Lane `acc:` verbatim:**

> `dira log` invoked to create a decision with two alternatives and a `derives_from`
> edge creates exactly one new file under `.dira/entries/`, that file passes E0's
> schema validator, and its id is the lowest unused number for its kind; 32 concurrent
> `dira log` invocations against one ledger produce 32 distinct ids and 32 files with

**What this lane is for.** `dira log` is dira's **write verb** — the command the
Claude Code skill calls with a complete entry (`dec-0003`), and the command a human
types when no agent is driving. It is *not* a `git log`-style history view; nothing
in E1 lists entries as a log. `dec-0002` bought "one write per mutation" and this
lane is where that property is either honoured or quietly lost.

## Constraints that bind this lane

- **Exactly one file per mutation.** Edges live on the subject entry. If a design
  needs two files written atomically, it is wrong (`dec-0002`). Assert the
  modified-path set, do not eyeball it.
- **Concurrent unattended writers are the normal case,** not an edge case: `Stop`
  hooks fire in parallel sessions on the same repo. Id allocation must be race-free
  and must not depend on a lock that only exists on a local filesystem, because the
  same allocator has to work over E7's `github` backend.
- **Every write goes through E1-L1's interface.** No `os.WriteFile` in the command
  layer (E1-L1's import-boundary test should catch a violation; make sure it does).
- **A partial write is worse than a failed write.** The ledger is the record; a
  half-written entry is corruption in the one artifact that is supposed to outlive
  the tool.
- **`cst-0002`:** a sixth kind is rejected with a message naming the constraint.
- Do **not** plan the ADR mirror (`dec-0009`) here. It is unowned in L0 and flagged
  upward in `docs/plan/lanes/E1.md`; the trigger is *acceptance*, which is E2's
  disposition flow. If you believe it must land in this lane instead, argue it in
  your output rather than adding it silently.
- Do **not** plan `dira init`, `dira sniff`, staged-entry disposition, or hook
  installation. Not this lane; see `docs/plan/lanes/E1.md`.

## Task bound and required fields

Produce **at most 8 tasks.** Each needs `id` (`E1-L2-T<n>`), `title`, `files`,
`acc:` (a command and an observable outcome, red before and green after — a
predicate a stub satisfies is a defect), and `depends_on`.

Provisional paths (reconcile against E0): `cmd/dira/` (the `log` subcommand and its
flag surface), `internal/ledger/` (id allocation, the write operation).

**Your task set must cover all of the following:**

1. The `dira log` flag/stdin surface: how a complete entry — kind, title, body,
   alternatives with `why_not` and `revisit_if`, edges, `source.hook`/`tier`,
   `confirmed_by`, `private` — is supplied by an agent non-interactively. An agent
   assembling a nested structure on a command line is a design decision; state it.
2. Id allocation that survives 32 concurrent writers with no collision and no
   local-filesystem-only assumption.
3. Validation before write: schema-valid or rejected, with the failing field named.
   An invalid entry must never reach the ledger.
4. Crash-safety of the single write, and the assertion that exactly one path changed.
5. Mutating an existing entry (adding an edge, bumping `updated`) as a single-file
   write that preserves the body byte-for-byte.

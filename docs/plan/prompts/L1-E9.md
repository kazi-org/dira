## Scope

Two issues at `kazi-org/kazi`. Both additive, neither breaking. This epic is
independent of every other and can run at any time.

**Ask 1 — register `portfolio` in `Kazi.CLI.Schema`.** It already emits
`schema_version` and a stable shape (`cli.ex:4249`), but the registry documents only
`apply`, `plan`, `bus`, `status`. Registering it makes dira's join surface a real
contract instead of an implementation detail dira happens to read. **This ask is
defensible on kazi's own terms regardless of dira** — an emitted-but-undocumented
`--json` shape is a gap in kazi's public contract whether or not anything consumes it.
Lead with that framing.

**Ask 2 — a post-disposition hook on `approve`/`reject`.** The highest-leverage
capture point in dira's design: an approval already *is* a decision event, so logging
it costs the user zero new ceremony.

**It must be a direct synchronous hook, NOT a `bus post`.** An earlier draft suggested
riding ADR-0067's session bus "rather than new infrastructure" and that was wrong on
verification: the bus is hosted by `kazi daemon`, and ADR-0067 states everything on it
"degrades gracefully when the daemon is not running: bus surfaces report 'no daemon'
cleanly and no-op." A disposition made with the daemon down would vanish silently —
disqualifying for a capture path. The bus is also age-bounded (~24h) and ~1KB-capped,
so it is the wrong durability and the wrong shape. Say this in the issue; it
pre-empts the obvious objection.

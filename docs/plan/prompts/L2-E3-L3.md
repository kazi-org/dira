# L2-E3-L3 — Inherit constraints across ledger boundaries without leaking private text

You are an L2 planner. You produce **tasks**, not code, and not lanes.

## Context

**Epic:** E3 — the enforcer. Constraints inherit **downward** through `derives_from`,
across ledger boundaries, and every `dira check` in every descendant ledger evaluates
them.

**Your lane:** E3-L3. Resolve `[parents]` from `.dira/config.toml`, read the parent
ledger **read-only**, collect its active constraints, evaluate them in the child, and
cite private ones **by ref only**. Plus the case that silently breaks the firewall: an
unreachable parent must be *reported*, never silently dropped — that configuration is
what a public clone has, so a quiet skip fails exactly where it matters.

**This lane is a security lane.** `cst-0003` is explicit: a private strategic note or
personal constraint committed into public git history cannot be un-published, and any
violation here is a security bug, not a UX bug. Plan its tests the way you would plan a
leak test, with a sentinel string and an assertion over every output byte — not by
inspecting output and judging it clean.

**depends_on:** E3-L1 (contract, fixtures), E3-L2 (the verb and its renderer).
**Cross-epic prerequisite:** E1's storage interface, used read-only against a second
ledger path.

**Your lane's `acc:` line, verbatim:**

> with a fixture parent ledger (`tier = "person"`) holding an active constraint whose
> body contains the sentinel `SENTINEL-PRIVATE-TEXT` and a child ledger whose
> `[parents]` points at it, `dira check "start a second side project"` from the child
> exits 2, cites `me:cst-0002`, and its combined stdout+stderr contains zero
> occurrences of `SENTINEL-PRIVATE-TEXT` and zero occurrences of the parent constraint's
> title — the same assertion holding for `--json`; a sha256 over the child's sorted
> `.dira/entries/` is identical before and after the run (read-time only, `cst-0003`
> rule 2); no dira invocation in the test writes any byte under the parent ledger path
> (assert by parent-tree digest, `cst-0003` rule 1); and with `[parents]` pointing at a
> nonexistent path the same command still exits on its *local* verdict while printing a
> line naming the unresolved parent and the number of constraints not evaluated.

## Fixed before you start

- **Private entries are cited ref-only always, not conditionally.** `cst-0003` rule 3
  and `docs/design.md` §7 phrase it as "where a check must cite a private constraint in
  a public context". Implemented literally that would require the binary to classify its
  own stdout as public or private, which it cannot — a pipe into a PR body looks like a
  terminal. So **any** entry with `private: true`, and **every** entry read from a
  `tier = "person"` ledger, is cited by ref (`me:cst-0002`) and never by text, in every
  mode. This is strictly tighter than the constraint, so it supersedes nothing.
- The enforcement set, the exit codes (`0`/`1`/`2`), and the message format are settled
  in `docs/plan/lanes/E3.md` and E3-L2. Inherited constraints render in the same block
  shape as local ones; the only difference is the namespaced ref and the absent text.
- `.dira/config.toml` already commits the `[parents]` shape:
  `sire = { path = "../../…", ref = "main" }`, currently commented out. Use it; do not
  invent a second config surface.

## The boundary you must not cross

`qst-0001` is **open** and blocks E5: *how does a public repo ledger resolve a parent ref
that lives in a private ledger?* Three candidate answers, none obviously right, and
answering it requires deciding who the public `.dira/` is for.

Your lane is safe only because of its scope: **resolve a parent that is present on this
machine, and report when it is not.** Do not decide what a public clone *displays* for a
dangling private ref, do not add alias or stub entries, and do not strip-on-publish.
Deciding `qst-0001` in passing pre-empts a blocked epic that L0 explicitly says must not
be planned below lane level yet. If a task you are drafting needs `qst-0001` answered,
that task belongs to E5 — say so instead of writing it.

Note also that this lane lands the `[parents]` reader E5 will build namespaced ref
resolution on. Keep it a narrow, reusable read path and say so in your output, so E5
extends it rather than writing a second one.

## The task bound

**≤8 tasks.** Each task needs: `id` (`E3-L3-T<n>`), `title` (one line, imperative),
`files` (actual paths), `acc:` (one machine-checkable predicate — a command and an
observable outcome), `depends_on` (task ids or `none`).

Seams where the work divides — **guidance, not your task list:** the `[parents]` config
reader; the read-only parent ledger open path; collecting inherited active constraints
and namespacing their refs; the privacy redaction in the renderer and in `--json`; the
sentinel leak test; the no-write / read-time-only digest assertions; the unresolved-parent
report path.

At least one `acc:` should be a pure negative-space predicate — a grep for the sentinel
across all output that fails red if the leak exists. A privacy rule with no test that
can fail is not enforced.

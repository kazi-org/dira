# L2-E3-L1 — Fix the conflict-detection contract and build the adversarial corpus

You are an L2 planner. You produce **tasks**, not code, and not lanes.

## Context

**Epic:** E3 — the enforcer (`dira check`, `dira supersede`, constraint inheritance,
`revisit_if` surfacing). It is the epic that makes dira more than a notebook.

**Your lane:** E3-L1. Decide *how* a free-text plan string is matched against the
ledger, record that decision as a real dira entry with its rejected alternatives, and
build the fixture ledgers plus the labeled corpus that E3-L2, E3-L3 and E3-L4 are all
graded against. The corpus is authored **before** any matcher exists and frozen by
checksum, so no later lane can reach green by deleting the rows it fails.

**depends_on:** none. No cross-epic prerequisite either — this lane is fixtures, a
schema-valid entry, and a written contract. It can be worked before E0 lands a Go
module; only the file paths assume E0's layout.

## The decision this lane must make and record

How does the binary get from `"add a background daemon to track run state"` to
`dec-0060`? Weigh at least these three, each with a real `why_not`:

1. **Lexical in the binary** — idf-weighted distinctive terms over the ledger plus
   exact multiword phrase hits, with a tuned threshold.
2. **Binary emits candidates, the live session adjudicates** — consistent with how
   `dec-0003` splits capture into a regex tier and a semantic tier.
3. **An optional schema field carrying explicit trigger terms** per constraint or
   alternative — moves the work to capture time.

**Binding, whichever wins:** `dira check` must reach a non-zero exit with **no model, no
network, and no agent present** (`dec-0003`, `cst-0004`). A design in which the exit code
depends on an agent having adjudicated is not admissible. An additive agent-assist mode
layered on a deterministic floor is admissible. If your decision needs a schema change,
it may add an optional field; it may never add a sixth entry kind (`cst-0002`).

Two things the decision should settle while it is open anyway:

- Whether a `constraint` gains an entry-level `revisit_if`. It has none today, so a
  constraint conflict currently has nothing to surface but "supersede it".
- Whether the check reads entry bodies or only frontmatter, and what that costs against
  `int-0002`'s latency posture.

## The task bound

**≤8 tasks.** Each task needs, and is incomplete without:

| Field | Rule |
|---|---|
| `id` | `E3-L1-T<n>` |
| `title` | one line, imperative |
| `files` | the actual paths it touches |
| `acc:` | one machine-checkable predicate — a command and an observable outcome, at task granularity. Not "the corpus is good" |
| `depends_on` | task ids, or `none` |

An `acc:` that is true before the task runs is a defect. So is one only a human can
judge.

Seams where the work naturally divides — **guidance, not your task list; you own the
decomposition and every `acc:` line:** the decision entry itself; the `daemon` fixture
ledger containing dec-0060 (plus a `staged` decision and a `rejected` decision, so
E3-L2 can prove the enforcement set); the corpus schema and its well-formedness test;
the conflicting rows; the near-miss rows; the checksum freeze; the `--json` verdict
shape that `schema/check.schema.json` will pin.

On the near-misses, the thing most likely to make this lane wrong: they must be
plausible strings a person would actually type, sharing vocabulary with an enforced
entry while genuinely not contradicting it. Adversarial word salad chosen to be
lexically indistinguishable from a real conflict makes E3-L2 impossible rather than
merely hard, and the failure will surface as an unreachable predicate two lanes later.

## Constraints that bind this lane

- **Pin every action to a 40-char SHA.** kazi does this throughout
  (`actions/checkout@34e114876b0b11c390a56381ad16ebd13914f8d5 # v4`). A public repo
  running an unpinned third-party action is a supply-chain hole, and matching kazi's
  convention means one habit across both repos.
- **`permissions: contents: read`** at minimum scope. Widen per-job only where a job
  genuinely needs it — nothing in this lane does.
- **Read the Go version from `go.mod`** (`actions/setup-go` with `go-version-file`).
  A version restated in YAML drifts from the one contributors actually build with,
  and then CI is testing a different toolchain than the one that ships.
- **The test count must be observable.** `go test ./...` on a module with no test
  files exits 0 and prints `no test files` — a green run proving nothing. Make the
  count or the package list visible in the log, or add a step that fails when zero
  tests ran. This is the whole reason the clause is in the `acc:` line.
- **Do not put the release pipeline here.** Tag-triggered builds, goreleaser, and
  release-please belong to E0-L4. This workflow is the push/PR gate only. If you add
  a `goreleaser check` step, it is E0-L4's to add after its config exists — a step
  referencing a file that does not exist yet makes CI red for the wrong reason.
- **Verification is two-sided or it is nothing.** The red half of the `acc:` line is
  done on a throwaway branch and reverted; it must never be pushed to `main`. Say so
  in the task that owns it, and name the branch-and-delete mechanics.
- **Platform matrix:** `ubuntu-latest` is mandatory. `macos-latest` is worth having
  because darwin-arm64 is the primary user platform and E0-L4 ships a darwin binary,
  but it doubles cost and queue time on every push. Decide, and record the reason
  either way in a comment.

## Also worth gating, if it stays cheap

`go vet ./...` and `gofmt -l .` are in the lane `acc:`. A linter beyond that
(golangci-lint) is defensible but adds a pinned binary, a config file, and a class of
failure unrelated to correctness. If you plan it, plan it as its own task with its own
predicate so it can be dropped without unpicking the rest.

## The task bound

**≤8 tasks.** Each task carries exactly: `id` (`E0-L3-T<n>`), `title`, `files` (real
paths, e.g. `.github/workflows/ci.yml`), `acc:` (one machine-checkable predicate at
task granularity), `depends_on`.

Predicates must reference an **observed run**, not the presence of a file.
`acc: .github/workflows/ci.yml exists` is vacuous — a workflow file that never runs,
or runs and skips everything, satisfies it. Prefer predicates checkable with
`gh run list` / `gh run view --log`, naming the expected conclusion.

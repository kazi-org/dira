The pitch to any repo with history is "import what you already have." kazi has 77+
ADRs; that corpus is the first real test.

The risk is precise: ADRs record *the choice*, and usually record context, but they
rarely record the **rejected alternatives with their why_nots** — which is the field
`dira check` reads and the field that makes `dira why` worth reading (dec-0003 makes
the same point about regex capture). An import that yields 77 entries with empty
`alternatives` arrays produces a ledger that cannot enforce anything: the ADR pile,
reindexed, with a nicer front end. That is a bad first impression at exactly the
moment a user is deciding whether dira is real.

Three options:

1. **Index, don't import.** Treat existing ADRs as read-only referenced documents —
   `dira why` can cite and link them without claiming them as entries. Preserves
   honesty about what is enforceable. Weakest immediate payoff.
2. **Semantic import via the skill.** Let the live session read each ADR and extract
   alternatives where they exist, marking entries `staged` where they don't. Better
   fidelity, but 77 staged entries is a triage queue nobody will finish.
3. **Import only what is cited.** Import an ADR the first time something references
   it. Lazy, ordered by real relevance, no queue — but the corpus stays mostly dark,
   so it does not answer "what did we decide" retrospectively.

Leaning toward (1) plus (3): index everything for retrieval, promote to a real entry
on first citation. Needs validating against the actual kazi corpus before committing.

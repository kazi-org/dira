Verified against kazi at `docs/adr/`, `lib/kazi/cli.ex`, and `lib/kazi/cli/schema.ex`
on 2026-07-29. Three seams, in order of how much upstream work each needs.

**1. Status join — works today, undocumented.** `kazi portfolio --json` is
implemented (`cli.ex:1254`, `portfolio_json/1` at `cli.ex:4249`) and emits
`schema_version`, `kind: "portfolio"`, `planned`, `by_repo` (repo → bucket →
entries), `fleet_remote`, `totals` (`{base, empty, rows: [{bucket, count, pct}]}`),
`todo`, `blocked` (each carrying `cause` and a `blocker` label), and `rate`. Its
bucket enum is exactly `done | running | blocked | todo | planned`, which maps
cleanly onto dec-0004's join table.

The catch: `portfolio` is **not registered in `Kazi.CLI.Schema`**, which documents
only `apply`, `plan`, `bus`, and `status`. So the shape is versioned but not
discoverable, and nothing in kazi's test suite pins it as a public contract. dira
should depend on it *and* ask upstream to register it — that is issue 1 of 2.

**2. Rationale linkage — works today, both directions, no upstream change.**
`kazi plan --adr --json` exists (`cli.ex:620`, ADR-0019) and mints the proposal ref
that `approve --json` flips (ADR-0049). Proposal refs look like
`prop-url-shortener-3f9c1a2b` and are stable, so `realized_by: kazi:prop-…` is a
durable edge upward.

The downward link needs **no new field**. Goal-files are TOML and already carry a
free-form `metadata` table — documented at `lib/kazi/goal/loader.ex:24` as
"table, optional, `Goal.metadata` (string-keyed map, **verbatim**)", read via
`Map.get(data, "metadata", %{})` (`loader.ex:640`) and stored with no validation.
So dira writes:

```toml
[metadata]
why = "dira:dec-0060"
```

and the loop closes today. (The loader also ignores unknown *top-level* keys
outright — it only `Map.get`s the keys it knows, so a bare `why =` would not error
either. Every "unknown X is a validation error" in that file concerns the *value* of
a known key — mode, provider, harness id, group ref — not the presence of an extra
one. `metadata` is nonetheless the intended and documented home, so use it.)

**3. Disposition capture — needs upstream.** `kazi approve <ref>` and
`kazi reject <ref>` are the single front door for accept/reject decisions, and
subscribing to them is the highest-leverage capture point in the whole design: every
approval is already a decision event, so logging it costs the user zero new
ceremony. But kazi emits no post-disposition hook today. Until it does, dira's skill
wraps the commands instead — correct behaviour, worse ergonomics. That is issue 2,
and it is the **only** seam that genuinely needs kazi to change.

The boundary itself is quoted from kazi's own README — it will never "decide what to
build — that's your judgment." That sentence is dira's charter: kazi is everything
downstream of a declared goal; dira is everything upstream of declaration.

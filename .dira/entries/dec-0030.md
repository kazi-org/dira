qst-0005 asks kazi's maintainer to register `portfolio` in `Kazi.CLI.Schema` and
names its own fallback if that is declined: *"(1) declined → dira pins the shape
and tests against a recorded fixture, accepting breakage risk on kazi
upgrades."* The founder's call on 2026-08-14 is to invoke that fallback now,
without waiting for a decline — qst-0005 stays `open` and genuinely unanswered
upstream (filing the two GitHub issues is E9's job, not this lane's), but dira's
own posture toward it changes: E4 no longer blocks on the answer.

The fact this leans on, verified against source rather than assumed:
`schema_version` is lockstep across kazi's entire `--json` surface —
`@run_schema_version 2` (`lib/kazi/cli.ex:95`), stamped by both `portfolio_json/1`
(`cli.ex:4249`) and `run_status_json/6`, the `status <ref> --json` encoder, and
neither is a private constant scoped to one command. Pinning `2` therefore pins
both surfaces this lane's client wraps, not just the unregistered one — the
version gate `internal/kazi` implements degrades to a `ContractDrift` flag,
never an error, exactly because a bump on either surface is the same signal
either way.

`internal/kazi` (E4-L1) is the concrete result: a typed client that decodes
`kazi portfolio --json` and `kazi status <ref> --json` against a committed
fixture corpus, never against a live binary in any test, and degrades
gracefully — a typed `Unavailable`, never a bare error or a silent empty
result — whenever kazi is absent, exits non-zero, prints something that does
not parse, or answers with the wrong `kind`.

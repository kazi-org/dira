Triage finding, 2026-09-02: internal/ledger/local/local.go Store.Create already does atomic exclusive-create (os.Link, fails if the target exists) and internal/ledger/write.go Add() already retries correctly on ErrExists, marking the id taken and advancing. This has been true since commit 4b7a0d9/b7c2f61 (2026-07-30), before v0.1.0/v0.1.1 and before every reported occurrence of issue #27. Git archaeology on hq's ledger (dec-0542/dec-0544, via macbook-chief) shows a single linear commit history with no merge and no discarded parent, ruling out a cross-branch merge collision and best fitting a single shared working tree. The most likely mechanism: an entry was created (successfully, atomically) but never committed, then deleted before commit (matching issue #35's exact bug), freeing its number for a later session's legitimate reuse -- not a live Add-vs-Add race. A persisted monotonic counter closes #35 unconditionally either way, and as a side effect turns two sessions independently bumping the same counter into a loud git merge conflict on the counter file, instead of a silent duplicate id.

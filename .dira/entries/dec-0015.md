## The decision

`EntryInfo.Version` on the local backend is the entry file's **git blob object
id** — `sha1("blob " + len + "\x00" + content)`, byte for byte what
`git hash-object` prints — and not the modification time and size it shipped
with. The derived read cache is a SQLite database at `.dira/cache/index.db`,
built with the pure-Go `modernc.org/sqlite`.

Together those two make dec-0002's "if the cache and the files ever disagree,
the files win" a guarantee rather than an expectation.

## Why the version had to change

E1-L1 shipped `mtime-nanos + size` and handed the choice on explicitly, with an
estimate that a content hash would cost about 13ms per full scan. Measured, it
costs **6.9ms against 2.2ms** — 4.7ms, roughly a sixth of the estimate, because
the estimate had folded in the YAML parse. Reading and hashing 200 entry files
is 241KB of I/O and a hash; it is not a parse.

At 4.7ms out of a 40ms budget, the heuristic is not worth defending. Its hole is
not theoretical: `accepted` and `rejected` are the same length, so the edit that
reverses a decision preserves the file's size, and any restore that preserves
modification times hides it completely. The acceptance test for that case is red
under the old scheme — verified by putting it back, not assumed — and green
under this one.

The git blob format rather than a bare hash is deliberate. E7's github backend
gets blob shas free from the Contents API, so both backends produce the same
version for the same content, which is dec-0005 actually paying off rather than
being asserted. And a human can reproduce dira's version with `git hash-object`
and no dira at all.

## How the cache is kept from becoming authoritative

Two structural mechanisms, neither of which is a habit anyone has to keep:

1. **Nothing dira prints comes from the cache.** `Index.Entry` and
   `Index.Entries` go straight to `ledger.Store` and read the file. The cache
   answers *which* entries a query is about; the files answer what each of them
   says.
2. **No query can run against an unreconciled cache.** `index.Open` reconciles
   before it returns — list the ledger, compare every content hash, re-read
   exactly what differs, drop rows for entries that are gone — and there is no
   method that reaches the database without that having happened. There is no
   fast path to skip, which is the form the lane's "staleness detection cannot
   be skipped for speed" constraint had to take.

An unwritable or read-only `.dira/cache/` is not an error. The same schema is
built in memory, the same SQL runs over it, a notice says why, and the exit code
is 0. One implementation, so a cached answer and an uncached one cannot drift
apart — which is a stronger claim than the differential test that also checks it.

## What it costs, measured

Over the 200-entry fixture, in process, spawn excluded:

| | |
|---|---|
| no cache — list, read and parse all 200 | 29.5ms |
| cache warm — hash scan, open, reconcile, render the brief | **14.8ms** |
| cache cold — the same, plus building the database | 55.5ms |
| `dira reindex` over 200 entries, one pass | 51.1ms |

The binary goes from 2.76MB to 11.79MB: **+6.52MB** for `modernc.org/sqlite` and
its translated libc, **+2.51MB** for the ledger codec's YAML and JSON Schema
dependencies. None of it is start-up time — process entry to `main` is
unchanged at ~3µs, and the median wall clock of `dira version` is the same for
both binaries — so the cost against int-0002 is download size and supply-chain
surface, not the latency int-0002 is about.

The cold number is the uncomfortable one and is recorded rather than buried: the
first invocation after `rm -rf .dira/cache` is nearly twice what having no cache
at all would cost, and it breaks even on the second. E1-L6 measures with the
cache deleted before every run, which measures a state that occurs once per
clone as though it were the steady state; that predicate should be read with
this number in hand.
